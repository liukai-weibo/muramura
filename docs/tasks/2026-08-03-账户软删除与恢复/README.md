# 账户软删除与恢复

> 创建于 2026-08-03，源码实现与自动化验证已完成，运行库尚未迁移。

现在的用户管理可以查看账户和调整管理员权限，但不能安全地停用一个账户。本任务要增加“删除账户”和“恢复账户”。这里的删除是软删除：用户仍保存在数据库中，只是不能再登录和使用系统。这样既能保留用户名、审计记录和业务数据归属，也能在以后恢复账户时避免数据断裂。

## 主要任务和改动原因

| 改动位置 | 需要做什么 | 为什么需要这样改 |
| --- | --- | --- |
| 数据库与 Migration | 新增 Migration 008，为 `users` 增加 `deleted_at`；扩展安全审计动作；源码最低 Schema 从 7 升到 8 | 系统需要一个明确、可查询的账户删除事实，不能根据角色、会话或页面样式猜测；启动版本门可以阻止新代码误连旧结构 |
| 认证与会话 | 登录和当前会话查询排除已删除账户；创建会话时再次由数据库确认账户仍有效 | 只修改登录查询会留下竞态：密码校验后、创建会话前账户可能刚好被删除，从而产生新的有效会话 |
| 管理业务与 MySQL Repository | 删除时在同一事务更新用户状态、撤销有效会话、撤销 `platform_admin` 并写审计；恢复时清除删除状态并写审计 | 这些事实必须全有或全无，否则可能出现“账户已删除但会话仍有效”或“恢复后权限被意外恢复”等不一致 |
| Contracts 与管理 API | 用户摘要增加 `deletedAt`；增加读取单个用户、删除账户和恢复账户接口；同步 OpenAPI 与 RPC 类型 | 后端、文档和前端需要使用同一份结构化状态；单用户读取用于写入结果未知时确认真实结果 |
| H5 用户管理 | 展示已删除状态；正常账户提供删除，已删除账户提供恢复；增加确认、禁用和结果未知处理 | 管理员需要看得见真实状态并避免重复操作；网络中断时不能把未知结果显示成成功，也不能自动重复删除请求 |
| 自动化测试 | 覆盖 Schema 7→8、事务回滚、登录/会话竞态、API 契约和 H5 状态 | 这些是软删除最容易留下安全漏洞和数据不一致的地方，必须有直接证据，而不是只验证页面出现了按钮 |

## 完成后的行为

管理员只能删除或恢复其他账户，不能操作自己。账户被删除后，现有会话立即失效，之后也不能重新登录；用户名、普通成员身份和业务数据继续保留。恢复后可以使用原用户名和密码重新登录，但旧会话不会复活，`platform_admin` 也不会自动恢复。

平台用户列表会同时显示正常账户和已删除账户。前端只相信 API 返回的 `deletedAt`。如果删除或恢复请求的响应丢失，页面保留“结果未知”状态，通过单用户读取确认，不自动再次提交写请求。

## 实施注意事项

- 不修改已经存在的 Migration 001–007，只新增 008；用户名唯一约束保持不变，已删除用户名不能被重新注册。
- 当前源码要求 Schema 8，日常运行库仍是 Schema 6。不能直接重启 API，必须先确认目标库并按顺序执行 007、008。
- 删除账户不能物理删除 `users`，也不能删除、转移或开放读取该用户的业务数据。
- 删除和恢复使用服务端时间；删除事务中的用户状态、会话、角色和审计必须一起提交或一起回滚。
- MySQL 自动化测试只使用随机临时数据库，不操作 `knowledge_base` 和 `knowledge_base_uat`，不删除 `mysql-data`，不手工修改 migration record。
