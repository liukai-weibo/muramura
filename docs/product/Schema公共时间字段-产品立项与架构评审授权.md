## 【结论】

产品立项「业务 base table 统一具备可观测的身份与时间审计字段」：每张在范围内的业务表应具备 `id`、`created_at`（创建后不变）、`updated_at`（业务写路径刷新）。本文件**仅授权架构师**输出最小任务书；**是否允许写代码：否**。

## 【当前阶段与编码门判断】

- 阶段：需求立项与架构评审门。
- 编码门：**未开**。未经架构最小任务书与后续独立产品编码授权，禁止修改 Schema、Migration、Repository、Contracts、API、H5、配置或运行库。

## 用户问题

当前各业务表的时间字段不统一（部分仅有 `created_at`，部分已有 `updated_at` / `deleted_at`），难以对「创建不变、后续写操作刷新更新时间」形成一致的产品事实与运维可观测性。希望先在产品层冻结口径，再由架构给出最小可信演进方案。

## 目标

使全部业务 base table 在产品语义上具备一致的：

1. `id`：行身份。
2. `created_at`：创建时间，创建后不变。
3. `updated_at`：每次业务更新，以及产品认定的删除类写操作（含既有软删路径），均刷新为操作发生时间。

## 产品冻结规则

1. 范围覆盖**全部业务 base table**；缺 `updated_at`（或等价产品语义）的表需补齐；已有字段的表对齐上述「创建不变、写操作刷新」语义，不得借机改变已封板业务含义。
2. `created_at` 一经写入不得被普通更新路径改写。
3. `updated_at` 必须在业务更新路径刷新；若表已有软删除（如 `deleted_at`），软删成功时也必须刷新 `updated_at`；硬删是否存在及如何记账由架构说明，产品要求删除类写操作不得留下「时间戳静止」的假象。
4. 产品只冻结**必须保存与可观测的业务事实**，不指定 DDL 形态、触发器、应用层赋值或 TypeScript 基类抽法——实现方式由架构任务书决定。
5. 不得修改已应用的 Migration `001`–`006` 文件内容；若需结构演进，只能以架构确认的新 Migration（例如 `007`）前进，并同步评估 `MYSQL_REQUIRED_SCHEMA_VERSION`。
6. 历史已存在行的回填策略由架构给出：必须可重复、可校验，且不破坏既有读取、Backup 恢复与软删语义。
7. 本项**不包含**用户改删、超级管理员、注册时可传角色，或其它权限模型扩展；该类需求另案立项。

## 【确认的范围】

- 全业务 base table 的 `id` / `created_at` / `updated_at` 产品语义对齐。
- 架构须盘点表级差异、Migration 方案、Repository/读模型/Backup 影响、启动门版本号、测试与运行库隔离策略。
- 必要产品、架构、QA 记录与当天贡献记录（仅在后续获编码授权并实际改动后）。

## 【不允许项】

- 不授权任何编码、`db:migrate`、手工 DDL、改 migration record、删 `mysql-data` / volume。
- 不改已应用的 `001`–`006` SQL 内容与 checksum 历史。
- 不新增超管、用户通用 CRUD、注册可选角色，不扩大平台角色白名单。
- 不改变已封板状态机、关联基数、软删/降级、Backup 格式业务语义（除非架构证明为字段对齐所必需且经产品二次确认）。
- 不把本立项解释为产品编码授权或运行库迁移窗口。

## 【需架构补齐的问题】

1. 当前 17 张（或以 `/health` 与 information_schema 实测为准）base table 中，哪些已具备三者、哪些缺失、哪些用了不等价命名。
2. 是否必须新增 `007`（或其它版本号），以及 `MYSQL_REQUIRED_SCHEMA_VERSION` 是否升至对应值。
3. 软删、会话撤销、审计只写等路径如何统一刷新 `updated_at`；无 `updated_at` 的只追加表是否允许架构给出有界例外并书面列出。
4. Backup 导出/恢复、读模型 DTO、OpenAPI 是否必须暴露 `updated_at`；最小可读契约是什么。
5. 历史行回填默认值规则（例如回填为 `created_at`）及校验方式。
6. 允许修改的层与文件清单、自动化测试矩阵、UAT/临时库隔离与两运行库只读快照要求。
7. 交付给产品编码授权的前置检查清单。

## 【验收标准】

1. 架构任务书列出范围内每张表的字段现状与目标语义，例外表（若有）有产品可裁决的明确理由。
2. 目标语义可观测：创建后 `created_at` 稳定；业务更新与约定删除类写操作后 `updated_at` 前进。
3. 历史行回填策略不破坏既有读取、软删展示与 Backup 恢复。
4. 迁移方案可重复、可校验；禁止改写已应用 migration 内容。
5. 任何实施（仅在后续编码授权后）必须附带日常库与 UAT 库隔离/未误伤证据；本立项阶段不执行迁移。
