## 一、产品结论

“探索主线”应进入产品路线，但它是新增长期层业务对象，不是事项状态、标签、类别、项目或 Todo 容器。

它解决的是“独立事项和复盘事实如何被可信地串成一段长期行动历程”，而不是计划、进度或自动下一步。因为涉及对象、结构化关系、主线—事项—复盘聚合、回收站和 JSON 备份，本项必须先完成架构评审；不得以前端状态、标题匹配或本地拼接绕过数据模型。

当前 MySQL 快速接入 Sprint 仍有完整浏览器主流程、备份恢复、重启验证和写入失败阻断复验未完成。探索主线不得插入其实现范围；本次只完成范围冻结与技术设计准备。

## 二、V1 冻结范围

### 1. 对象与关系

- 正式名称：探索主线。
- 一条探索主线仅包含名称；名称为必填。
- 允许空主线。
- 允许改名。
- 第一版不设主线自身状态、优先级、日期、描述、目标、阶段、提醒或完成度。
- 一条事项可关联 0 或 1 条探索主线；一条探索主线可关联 0 至多条事项。
- 关联只能由用户明确建立、调整或移除；不得按文本、时间、状态或相似性推断。

### 2. 创建与调整

- 用户可在探索主线列表独立创建主线。
- 用户可在快速捕获中按需选择已有主线，或明确“创建并归入”新主线。
- 用户可在主线详情内创建事项；“创建事项 + 关联当前主线”必须是单次原子业务写入。
- 事项详情支持归入、改归入或移除主线关联。
- 未关联主线的快速捕获主流程保持不变；主线选择永远可跳过。

### 3. 浏览与定位

- 工作台新增低频一级导航“探索主线”；默认仍进入“事项”。
- 桌面端采用左侧主线列表、右侧详情；小屏采用列表到全屏详情的单列返回层级。
- 列表显示名称和最近关联事项的标题、真实状态；空主线显示“暂无关联行动”。
- 主线详情显示上下文捕获和按事项创建时间倒序的探索历史。
- 已复盘事项只展示 Application 提供的结构化复盘事实摘要；无法取得时明确提示在事项中查看，前端不得伪造摘要。
- 历史中的“查看”必须切回事项工作台、选择该事项真实状态并打开事项详情。
- 已放弃事项默认收纳在按需展开的低频记录；回收站事项不显示在主线历史。

### 4. 删除、恢复与备份的产品语义

- 删除探索主线必须是可恢复的软删除 / 回收站语义；不得删除、改写或解除其关联事项和复盘事实。
- 被删除主线不在正常主线列表或关联选择器显示；关联事项仍以其自身状态独立运行。
- 恢复主线后，原有可信关联重新可见。
- 删除主线期间，事项详情对仍指向该主线的关联应诚实降级为“原探索主线已删除”，不得自动改归入或伪造无关联。
- JSON 导出与恢复必须保留探索主线、关联和删除状态；旧备份在缺少该结构时应安全恢复为空主线关系，不能失败或虚构关系。

## 三、明确非目标

- 子任务、勾选、批量拆解、项目看板。
- 进度条、完成率、主线内事项总数、连续天数、等级、积分。
- 日期、日程、提醒、阶段、优先级或目标数值。
- 自动生成下一行动、AI 推荐、模板或基于相似性的自动归类。
- 一个事项关联多条主线。
- 用探索主线代替方法，或改变事项既有状态机与复盘语义。
- 真实 IndexedDB 历史迁移、双写、同步或浏览器直连 MySQL。

## 四、实施计划与阶段门

### 阶段 0：先关闭当前 Sprint

前提：完成当前 MySQL 快速接入 Sprint 的浏览器完整闭环、JSON 导出—清库—恢复、API/MySQL 重启后页面验证，以及写入失败阻断复验。

产物：当前 Sprint 验收和封板。探索主线实现不得与该验证混合。

### 阶段 1：架构评审与契约冻结

责任：架构师。

需冻结：

- MySQL 最小实体、事项 0..1 关联和软删除模型；Migration 与既有事项兼容策略。
- 主线列表、主线详情历史、可用主线选择器、事项详情关联信息的 Application 读模型与 API 契约。
- 创建事项并关联主线的原子写入契约；关联改动与移除契约。
- 名称规范化、长度上限、唯一性和冲突错误由 Application 层负责。
- 主线删除 / 恢复、事项删除 / 恢复、缺失关联、已放弃收纳的可信读写语义。
- JSON 备份版本演进、旧备份降级和恢复顺序。
- Application、Repository、API、前端分别允许修改的范围和自动化测试策略。

完成门：架构任务书、接口契约、迁移与备份策略经确认；否则不得开始数据层或前端编码。

### 阶段 2：交互与视觉冻结

责任：设计师；基于阶段 1 的可靠读模型与生命周期约束。

需产出：

- 一级低频导航、桌面列表—详情、小屏列表—详情的明确状态图。
- 创建、改名、删除确认、恢复、主线选择与“创建并归入”的交互稿。
- 主线内捕获的加载、空输入、创建失败、读取失败、空主线、缺失关联和低频已放弃记录状态。
- 历史条目的状态、复盘摘要降级、查看事项定位及桌面/小屏验收标注。

完成门：不新增业务语义，且前端可按标注直接实施。

### 阶段 3：数据与 Application / API 实现

责任：后端（Data / Application / Repository）。

实施顺序：

1. MySQL Schema 与 Migration。
2. 实体、关系、名称校验和删除恢复业务规则。
3. 备份导出、恢复与旧备份安全降级。
4. 主线列表 / 历史读模型与 API。
5. 原子创建事项并关联主线、关联调整 / 移除、主线改名 / 删除 / 恢复 API。
6. 自动化覆盖创建、重名、空主线、原子写入、状态变化、删除恢复、事项回收恢复、缺失关联和备份恢复。

完成门：UAT MySQL 上的 API 与自动化契约验证通过；前端不直接读写底层数据。

### 阶段 4：前端实施

责任：前端。

实施顺序：

1. 一级导航与主线列表 / 详情的局部页面状态。
2. 主线创建、改名、删除恢复和加载 / 失败 / 空态。
3. 全局快速捕获可选关联、创建并归入，以及事项详情关联调整。
4. 主线详情上下文捕获与原子创建反馈。
5. 事实时间线、复盘摘要降级、低频已放弃记录与“查看”回到真实事项状态。
6. 小屏降级、异步竞态和用户输入保护。

完成门：所有页面只消费 Application/API 的结构化读模型；不以标题、状态文本或本地缓存推断关系。

### 阶段 5：UAT、产品验收与封板

责任：QA → 产品。

最小验收闭环：

- 创建空主线、改名、删除、恢复。
- 快速捕获不选主线仍正常；选择已有主线或创建并归入后写入可信关系。
- 主线内创建失败时草稿保留；成功后历史更新且不跳转详情。
- 事项详情能改归入、移除关联；一条事项不能多归属。
- 所有事项状态在主线历史中按规则呈现；复盘摘要和缺失关联诚实降级。
- 查看历史事项能回到正确状态池与详情。
- 事项 / 主线删除恢复和 JSON 导出—清库—恢复后关系不丢失、不伪造。
- 日常库与 UAT 库严格隔离；以 `/health` 返回的 database 作为现场证据。

完成门：仅在完整闭环、备份恢复和人工桌面/小屏验收通过后封板。

## 五、风险与控制

| 风险 | 控制 |
| --- | --- |
| 主线滑向项目管理 | 严格禁止进度、阶段、计划和自动下一步；主线仅串联事实。 |
| 前端按文本或时间猜关系 | 所有关系与摘要来自结构化 Application 读模型。 |
| 创建事项后关联失败 | 使用原子写入契约，不允许前端二次补写。 |
| 主线删除导致历史丢失 | 主线与事项独立软删除，恢复后恢复可见关系。 |
| 旧数据与备份不兼容 | Migration 默认事项无主线；旧备份安全降级为空关联。 |
| 跨 Sprint 干扰 MySQL 主链路 | 阶段 0 未封板前不进入实现。 |
