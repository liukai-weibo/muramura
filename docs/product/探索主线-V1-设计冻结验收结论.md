## 一、验收结论

设计总体符合产品范围与架构边界：它将探索主线保持为低频、长期事实历程，未滑向项目、计划、进度或 Todo 容器；桌面与小屏层级、删除恢复、关联降级、历史定位、空态与失败态均符合已冻结原则。

但设计冻结不能标记为完全通过，须在 API 路由矩阵确认前修正一项原子语义并补齐两类读模型边界。完成以下三项后，设计视为正式冻结完成。

## 二、已通过的设计范围

- 一级导航中事项保持默认高频，探索主线为低频一级视图，设置不移位。
- 桌面端采用列表—详情；小屏采用列表—全屏详情—返回。
- 主线创建、改名、软删除、恢复、名称冲突及已删除关联的交互不超出既有业务语义。
- 事项详情关联、关联移除与不可用关联的诚实降级符合事项 0..1 可信关系约束。
- 探索历史按事项创建事实排序；已放弃记录低频收纳；回收站事项不进入历史；复盘摘要只使用结构化读模型。
- 查看事项切回真实状态池并重新读取详情，未使用前端猜测或本地缓存替代。
- 未引入进度、完成率、事项计数、计划、日期、提醒、子任务、看板、自动下一步、AI 推荐或多主线关联。

## 三、正式冻结前必须修正与补齐的项

### 1. 快速捕获“创建并归入”不得先写入主线

当前设计稿第 6.3 节描述“创建并归入”后先成功创建主线、但事项尚未创建。这与已冻结的产品和架构原子语义冲突。

正式规则改为：

```text
快速捕获中输入新主线名称
→ 仅将“新主线名称”暂存为未提交表单选择
→ 用户点击“加入想试试”或“加入以后再说”
→ 单一原子请求创建主线 + 事项 + 初始状态事件 + 关联
→ 全部成功才显示创建成功
```

- 取消新主线选择只清除表单暂存，不产生任何业务写入。
- 创建失败保留事项输入、新主线名称与初始状态选择；不留下空主线或半成型事项。
- 独立“新建探索主线”入口仍可单独创建允许为空的主线。

### 2. “当前关联事项”读模型需在 API 矩阵明确

设计中的“当前关联事项”是对主线历史的有限、按状态分组的投影视图，不可由前端从历史列表自行筛选、排序或截断后伪造。

API 路由矩阵须明确以下任一最低成本方案：

- 在主线详情历史读模型中返回结构化 `currentAssociatedItems`；或
- 提供独立只读 Contract。

无论采用哪种方案，必须冻结：状态范围、每状态展示上限、稳定排序、超过上限时“查看该状态下的事项”的真实定位参数，以及空态语义。不得返回事项总数、完成率或进度数据。

### 3. 已删除主线管理列表需在 API 矩阵明确

设计中的“已删除主线”管理入口需要结构化列表能力。架构当前的活跃主线列表只返回 `deleted_at IS NULL` 的记录，因此 API 路由矩阵须明确：

- 已删除主线的受限只读列表与稳定排序；
- 进入详情、查看关联事实、恢复的允许范围；
- 不展示数量，不提供永久删除；
- 与活跃主线选择器严格隔离。

## 四、阶段门确认

阶段门继续有效：当前 MySQL 快速接入 Sprint 未完成浏览器完整闭环、JSON 导出—清库—恢复、API / MySQL 重启验证及写入失败阻断复验前，探索主线不得进行任何数据层、API 或前端编码。

当前正确口径仍为：MySQL 是当前 H5 运行数据源；不得提前称为唯一运行主库。

## 五、后续授权

架构师可在不写业务代码的前提下，产出 API 路由矩阵、DTO、稳定错误码与未知写入结果策略，并解决本结论第三节的三个契约缺口。

产品确认 API 矩阵、当前 MySQL Sprint 正式封板、设计稿据此修订完成后，才允许流转数据 / Application / Repository 工程师制定并执行实施任务书。前端继续等待数据 / API 契约和后端实现完成。
