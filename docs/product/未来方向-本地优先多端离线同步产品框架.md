# 未来方向：多端产品路线与后续离线同步框架

> 状态：方向性记录，未立项、未冻结、未授权编码。
>
> 创建日期：2026-07-29
>
> 本文描述未来产品形态，不替代 `docs/product/当前运行事实.md`，不改变当前 MySQL 本地运行路径、Backup V3、局域网边界或任何已封板范围。

## 一、要解决的用户问题

用户希望在 Web、电脑桌面端与安卓端使用同一套个人行动系统：

- 初期可先在线使用，在不同设备上看到同一份可信数据；
- 先完成 Web、桌面与安卓的真实使用闭环；
- 日常使用不需要由每位用户维护 MySQL 或 Docker；
- 在产品稳定后，再增加断网可编辑与联网同步；
- 保留本地优先、数据可导出、可恢复和不被平台锁定的原则。

近期这不是“本地数据库同步”项目，而是一个以统一在线数据源支撑多端访问的产品方向。离线优先与多端同步是后续独立阶段。

## 二、目标产品形态

```text
共享领域规则、契约、API 与测试
├─ Web：浏览器工作台与局域网入口
├─ Desktop：Windows / macOS 桌面应用壳，复用工作台 UI
└─ Android：面向随手捕获、查看和基础编辑的移动 UI

近期客户端
└─ 通过受控在线 API 读写统一服务端事实

后续离线阶段的客户端
├─ 内置本地 SQLite 数据库
├─ 离线直接读写本地数据库
└─ 联网后通过同步服务上传与拉取变更
```

近期桌面端不应继续把 MySQL Docker 当作每位用户的正式运行时依赖，而应连接受控在线服务。后续若立项离线，SQLite 才作为嵌入式离线存储引入；它不是当前开发前置条件。

## 三、范围与非目标

### 方向目标

1. 一个受控在线数据源支撑 Web、桌面和安卓端。
2. Web 优先验证，桌面端随后提供稳定工作台，安卓端先服务高频捕获。
3. 一套共享的领域规则、状态语义、同步协议和测试基线；各端仅分离 UI 与平台外壳。
4. 用户可导出、迁移和恢复自己的完整数据。

### 当前明确非目标

- 不在当前 Sprint 中实施云端服务、账号体系、安卓应用、SQLite 替换或同步。
- 不建立三条长期 Git 代码分支，也不维护三套领域模型、状态机或同步逻辑。
- 不采用客户端 SQLite 与当前 MySQL 双写、按时间戳覆盖或无规则合并。
- 不默认新增多人协作、共享空间、公开链接、组织管理、广告或数据售卖。
- 不以“实时”承诺无限制毫秒级一致；离线设备以最终一致为目标，在线时可尽快同步。

## 四、推荐实施顺序

### 阶段 A：当前本机 Web / LAN 产品继续验证

保持当前 MySQL 本地运行、Backup V3、日常/UAT 隔离和已冻结业务规则，完成本机、Docker 与 LAN 使用验证。此阶段不公网发布，也不引入账号或云端数据。

### 阶段 B：在线服务与 Web Beta

独立立项建立受控在线服务，使用户能在受支持的网络环境中访问同一份数据：

- 身份、单用户数据隔离、服务端存储、传输安全与运营备份；
- 从当前本地 Backup 的显式、可验证导入，而不是复制运行库；
- 保留用户完整导出、恢复与数据迁出能力；
- 先发布功能型 Web Beta，验证在线使用是否成立。

### 阶段 C：桌面端发布

以 Web 工作台为基础，用 Tauri 或 Electron 提供 Windows / macOS 桌面应用：

- 复用 Web UI、共享领域规则、契约和在线 API；
- 不要求第一版离线编辑；无网络时诚实显示不可写状态；
- 先验证安装、升级、桌面工作流和持续使用价值。

### 阶段 D：安卓端

安卓端先实现高频价值闭环：快速捕获、查看和基础编辑。它复用同一在线 API 与领域规则；复杂工作台、完整设置、离线队列和恢复能力另行评估，不要求第一版等同桌面端。

### 阶段 E：离线编辑与多端同步（后置、独立立项）

在 Web、桌面和安卓已有真实在线使用后，再评估离线编辑是否值得投入。若立项：

- 客户端引入 SQLite 作为离线即时事实来源；
- 同步服务传递业务变更，而非复制 SQLite 文件或让客户端直连服务端数据库；
- 设备身份、冲突收敛、离线 outbox、幂等、恢复与 Backup 并发须重新冻结；
- 先从双桌面设备试点，再扩展到安卓与 Web。

## 五、数据与同步原则

1. 近期在线阶段只有服务端确认的读写结果才是跨设备可见事实；客户端不得伪造已保存或已上传。
2. 服务端与客户端均保留完整导出、恢复、迁出与可验证备份能力。
3. 离线同步阶段才引入本地 SQLite、变更标识、顺序、冲突收敛和离线队列；不得以当前数据库双写作为过渡方案。
4. 不以客户端时间戳、文案或计数猜测冲突结果。
5. 事项状态迁移、探索主线关联、删除/恢复、方法版本、复盘证据与 Backup 恢复都必须分别定义冲突与优先级规则。
6. 无法自动安全合并时，必须保留双方事实并要求用户明确处理；不得静默丢弃数据。

## 六、代码组织原则

推荐单一主干、monorepo 组织：

```text
packages/
  contracts/       跨端稳定数据契约
  domain/          领域规则与状态语义
  sync/            同步协议、变更模型和冲突规则（后续离线阶段新增）
apps/
  web/             浏览器入口
  desktop/         桌面外壳与平台集成（未来新增）
  android/         安卓 UI 与平台集成（未来新增）
services/
  sync/            同步服务（未来新增）
```

这不要求 Web、桌面和安卓共享所有 UI。共享的是规则和可信数据能力；桌面与安卓可以拥有不同的导航、布局、文件能力和交互节奏。

## 七、必须先完成的产品与架构裁决

在任何编码前，产品经理与架构师须分别冻结：

1. 在线服务的数据部署位置、用户范围、账号、数据隔离、传输安全与隐私策略。
2. 当前本地 Backup 到在线账户的显式导入、导出、回滚、灾难恢复与跨版本兼容策略。
3. Web、桌面与安卓首版各自必须支持的用户任务和非目标。
4. 桌面端及安卓端技术选型，确认可复用哪些共享包。
5. 后续是否值得建设离线编辑；若值得，再单独冻结设备身份、变更模型、冲突规则、删除/恢复和 Backup 恢复与同步的互斥边界。

## 八、启动条件

只有同时满足以下条件，才可从方向记录进入正式立项：

- 有持续、明确的在线多端使用证据；
- 产品已定义首个可验收的在线 Web Beta 范围与非目标；
- 架构评审已覆盖数据可信性、安全、备份、迁移和故障恢复；
- 不与当前已封板范围、进行中的授权任务或 UAT 隔离要求冲突；
- 获得独立、书面的产品编码授权。

## 九、当前结论

推荐路线是：当前本机 Web / LAN 验证 → 在线服务与 Web Beta → 桌面端 → 安卓端 → 基于真实需求再立项离线 SQLite 与多端同步。当前系统继续按本地 MySQL 运行，本文不构成任何代码、配置、数据库、云端服务、同步服务或发布授权。
