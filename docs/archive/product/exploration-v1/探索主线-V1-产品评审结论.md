# 探索主线 V1 产品评审结论

> 评审日期：2026-07-24
>
> 结论：产品取舍确认；授权设计冻结；当前禁止编码。
>
> 依据：`当前运行事实.md`、`探索主线-Sprint-产品范围冻结与实施计划.md`、`../architecture/探索主线-V1最小架构评审与技术任务书.md`

## 一、结论

探索主线 V1 按架构任务书的最小模型推进。它用于串联独立事项与复盘事实形成长期行动历程，不是类别、项目、计划或 Todo 容器。

产品确认以下架构取舍，并维持当前 MySQL 快速接入 Sprint 完整封板前禁止探索主线编码的阶段门。

## 二、已确认取舍

### 1. JSON 备份版本演进：确认

新增 `BackupDocumentV3` 与 `explorationTracks` 集合。

- v1 / v2 旧备份导入时，探索主线集合安全降级为空，既有事项视为无主线关联。
- 旧备份恢复不得失败、猜测、回填或生成主线关联。
- v3 备份必须保留探索主线、软删除状态与事项关联。
- 任一新备份中的关联引用不可信或断裂时，恢复必须整体拒绝并保持零业务写入；不得为通过恢复而删除、伪造或重连关系。

理由：主线与事项关系属于业务事实，不能藏在无版本的可选字段中；兼容必须保守，不能以自动推断污染历史。

### 2. 主线名称全生命周期唯一：确认

探索主线规范化名称在所有未物理删除记录中全局唯一，包含软删除主线。

- 删除主线不释放名称。
- 用户希望继续使用同一长期脉络时，应恢复原主线，而非新建同名副本。
- 不允许因删除后同名新建、再恢复旧主线而出现两个不可裁决的同名长期历程。

理由：探索主线是长期事实载体，不是可随意复用的临时标签；保持身份连续性优先于短期输入便利。

### 3. V1 不支持主线物理永久清理：确认

V1 中主线仅可软删除与恢复，不加入物理 purge、墓碑清理或级联清理。

- 删除主线不删除、解除或改写关联事项、复盘、方法与状态事件。
- 关联事项在主线删除期间应诚实显示“原探索主线已删除”，不得伪装成未关联。
- 未来如需永久清理，必须以独立产品需求重新定义历史可信性、备份恢复与关联降级，不得作为本 Sprint 顺带实现。

理由：主线软删除记录是已有关联事实能够稳定解释的必要锚点；当前没有真实摩擦证据支持引入高风险清理策略。

## 三、阶段门与授权

### 当前 MySQL 快速接入 Sprint：保持优先

确认维持阶段门：当前 Sprint 完成以下验收并封板前，探索主线不得进入数据层、API 或前端编码：

- 浏览器级完整主流程；
- JSON 导出、清库、恢复；
- API / MySQL 重启后的页面验证；
- 写入失败阻断的根因修复与复验。

当前可用表述仍为“MySQL 是当前 H5 运行数据源”，不得提前表述为唯一运行主库。

### 授权设计师开始设计冻结：是

设计师可基于已冻结产品范围和架构边界，开始探索主线 V1 的交互与视觉冻结，包括：

- 工作台一级低频导航；
- 桌面端主线列表—详情、小屏列表—全屏详情—返回层级；
- 创建、改名、软删除、恢复确认；
- 快速捕获可选关联、“创建并归入”、事项详情关联调整；
- 主线内捕获、探索历史、已放弃低频收纳；
- 空态、加载、失败、已删除主线关联和不可用关联的诚实降级；
- “查看事项”回到真实事项状态与详情的交互要求。

设计师不得引入进度、完成率、计划、日期、提醒、子任务、自动归类或任何新的业务语义。

### 授权数据 / Application / Repository 实施：有条件允许

仅在以下前置全部达成后，才允许流转实施：

1. 当前 MySQL 快速接入 Sprint 已正式封板；
2. 设计冻结完成，且未超出本文件与架构任务书边界；
3. API 路由矩阵、DTO、错误码、未知写入结果处理经产品确认；
4. 实施任务书明确 Migration、备份、读模型、原子写入与自动化测试验收项。

前端实施继续等待数据 / Application / Repository 能力、API 契约和设计交付完成后才可开始。

## 四、范围保护

本结论不授权：

- 双写、同步、回填、IndexedDB fallback 或浏览器直连 MySQL；
- 事项状态机、复盘工作流、方法语义或既有回收站规则变更；
- 子任务、进度、计划、日期、提醒、AI 推荐或自动推断关联；
- 一个事项关联多条探索主线；
- 在当前 Sprint 封板前提前编写探索主线业务代码。
