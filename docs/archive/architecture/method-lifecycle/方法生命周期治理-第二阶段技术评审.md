# 方法生命周期治理 — 第二阶段技术评审与架构冻结草案

> 状态：**P0/P1 已由 QA 独立验收通过；本文件仅冻结数据方案，尚未授权实施。**
> 前置验收：`docs/architecture/数据可信性与备份恢复修复-技术评审.md` 对应修复已通过 QA（2026-07-21）。
> 产品裁决来源：`docs/archive/architecture/method-lifecycle/方法生命周期治理-技术预评审.md`。

## 【技术结论：可行】

产品已确认采用“软删除 30 天可恢复 + 到期永久清理后保留最小历史墓碑”的方案 B。该方案可以在本地优先架构中稳定实现，但它是一次受控的数据生命周期扩展，必须同时修改 Contracts、Application、Repository、IndexedDB Schema / Migration 与 JSON 备份。

推荐将方法生命周期明确分为：

```text
可用方法
→ 已移入回收站的方法（30 天内可恢复，正文仍存在但不可复用）
→ 已永久清理的方法墓碑（正文已删除，历史关系仍可解释）
```

墓碑不是 UI 文案、不是隐藏方法副本，也不是可恢复对象；它是备份可校验、关系可追溯的最小结构化历史事实。

## 【已冻结业务语义】

### 1. 回收站期内

```text
Method.deletedAt 存在
→ 方法、版本、证据、方法应用关系仍存在
→ 正常列表、全局搜索、行动发起、验证与修订候选均不可见
→ 历史关联显示“关联方法：{title}（已移入回收站）”
→ 30 天内恢复后重新可用，既有关系不改写
```

### 2. 到期永久清理后

```text
删除：Method 与 MethodVersion 的全部可复用正文
保留：MethodTombstone、MethodEvidence、MethodApplication
→ 历史关联显示“关联方法：{title}（已永久清理）”
→ 墓碑不可用于行动、验证、修订、搜索或正文恢复
```

### 3. 事实关系的保留标准

产品要求保留的不只是“名称曾存在”，还包括：

```text
事项曾实际使用哪个方法及哪个版本
复盘曾形成 / 验证 / 修订哪个方法
```

因此只保存 `{ methodId, title, purgedAt }` **不足够**：它无法在版本正文删除后可靠区分某条 `MethodEvidence` 是形成、验证还是修订。该关系不能在前端按时间或版本号猜测。

## 【最小新增能力】

### Contracts：新增墓碑与版本来源索引

建议新增：

```ts
interface MethodTombstoneVersion {
  version: number
  sourceReviewId?: string
}

interface MethodTombstone {
  methodId: string
  title: string
  purgedAt: string
  versions: MethodTombstoneVersion[]
}
```

字段边界：

| 字段 | 用途 | 明确不保存 |
|---|---|---|
| `methodId` | 复用原稳定身份，与既有应用 / 证据关联 | 新 ID、推测关联 |
| `title` | 历史展示的最后已知方法名称 | 步骤、适用情况、不适用情况 |
| `purgedAt` | 生命周期事实与审计 | 恢复正文所需快照 |
| `versions[].version` | 校验历史 `MethodApplication.methodVersion` 是真实曾存在的版本 | 版本正文 |
| `versions[].sourceReviewId` | 精确识别证据为形成 / 修订；未命中时才是验证 | 时间推断、文案推断 |

`versions` 只保留版本号与来源复盘结构化引用，不保留标题、步骤或其他版本正文。它是保留“关系事实”的最小必要索引，而非隐藏版本副本。

### 结构化读取模型

将现有方法应用上下文演进为：

```ts
type MethodApplicationContextResult =
  | { status: 'no-association' }
  | {
      status: 'available'
      application: MethodApplication
      method: Method
      version: MethodVersion
    }
  | {
      status: 'method-in-trash'
      application: MethodApplication
      method: Method
      version: MethodVersion
    }
  | {
      status: 'method-purged'
      application: MethodApplication
      tombstone: MethodTombstone
    }
  | {
      status: 'unavailable'
      application: MethodApplication
      reason: 'method-missing' | 'version-missing' | 'method-and-version-missing'
    }
```

约束：

- `method-in-trash` / `method-purged` 是正常、可预期的生命周期状态，不能复用 P1 的 `unavailable`；
- `unavailable` 继续专用于异常断裂；
- 前端仅可根据 `status` 渲染；
- `method-in-trash` 与 `method-purged` 都不提供默认验证、可选验证、修订或行动发起资格；
- 用户主动选择其他正常可用方法属于新操作，不能修复或覆盖旧关系。

### 方法证据历史读模型

现有 `MethodEvidenceDetail` 依赖活跃 `Method` 与 `MethodVersion` 计算关系。永久清理后，该计算不能再依赖已删版本正文。

需要新增或扩展 Application 读模型，依据以下结构化事实计算：

```text
MethodEvidence.methodId
+ Review
+ 活跃 MethodVersion.sourceReviewId
或 MethodTombstone.versions[].sourceReviewId
```

判定规则：

```text
证据 reviewId 命中 version 1 的 sourceReviewId → formation
证据 reviewId 命中 version > 1 的 sourceReviewId → revision
证据存在但未命中任一版本来源 → validation
关系实体缺失或同一 reviewId 命中多个版本 → unknown
```

不得以 `createdAt`、当前方法版本号、标题或复盘文案推断。

## 【永久清理事务与引用完整性】

### 方法到期清理

对 `deletedAt <= cutoff` 的方法，在**同一个 IndexedDB 读写事务**内：

1. 读取该方法、全部版本、全部 `MethodEvidence`、全部 `MethodApplication`；
2. 生成 `MethodTombstone`：
   - `methodId = method.id`；
   - `title = method.title`；
   - `purgedAt = now`；
   - `versions = versions.map(({ version, sourceReviewId }) => ({ version, sourceReviewId }))`；
3. 写入墓碑；
4. 删除全部 `MethodVersion`；
5. 删除 `Method`；
6. **保留** `MethodEvidence` 与 `MethodApplication`；
7. 提交事务。

写入墓碑后，备份严格校验中的方法引用有效目标变为：

```text
活跃 / 回收站 Method
或
MethodTombstone
```

禁止：

- 删除 `MethodEvidence` 或 `MethodApplication` 以让校验“通过”；
- 把方法应用关系重新连接到同名 / 相近方法；
- 用本地 UI 缓存补历史名称；
- 写入不含 `versions` 索引的墓碑。

### 事项到期清理与墓碑协作

事项永久清理时，仍按已验收 P0 策略删除该事项的 `Review`、`MethodEvidence`、`MethodApplication`、状态事件与事项。

额外约束：

1. 对被删除 `Review`，清空所有活跃 `MethodVersion.sourceReviewId`；
2. 对被删除 `Review`，也清空所有 `MethodTombstone.versions[].sourceReviewId`；
3. 若某墓碑不再被任何 `MethodEvidence` 或 `MethodApplication` 引用，删除该墓碑；
4. 以上与事项清理必须在同一事务完成。

这表示：已永久清理的方法的关系只在其关联的历史事项 / 复盘仍存在时保留；当历史承载对象本身被永久清理后，墓碑不再被无期限孤立保留。

## 【备份与恢复策略】

### Backup v2

`BackupDocument` 升级到 v2，并新增：

```ts
methodTombstones: MethodTombstone[]
```

v2 校验不变量：

1. `Method.id` 与 `MethodTombstone.methodId` 全局互斥；
2. 每条 `MethodEvidence.methodId` 必须指向 `Method` 或 `MethodTombstone`，且 `reviewId` 必须存在；
3. 每条 `MethodApplication.methodId` 必须指向 `Method` 或 `MethodTombstone`，且 `itemId` 必须存在；
4. 指向活跃 / 回收站 `Method` 的应用，其 `methodVersion` 必须存在于 `MethodVersion`；
5. 指向墓碑的应用，其 `methodVersion` 必须存在于 `MethodTombstone.versions`；
6. `MethodTombstone.versions[].sourceReviewId` 若存在，必须引用存在的 `Review`；
7. 墓碑不得含步骤、适用情况、不适用情况、版本正文等禁止字段；
8. 回收站方法仍是 `Method`，必须连同全部版本正常导出。

### v1 导入兼容

- v1 备份没有 `methodTombstones`，导入时归一化为 `[]`；
- 保留已验收的兼容规则：仅断裂的可选 `MethodVersion.sourceReviewId` 可清空后继续校验；
- v1 中其他必填引用断裂仍严格拒绝；
- 导入 v1 后下一次导出统一生成 v2；
- 不尝试从 v1 数据伪造墓碑。

## 【可复用现有能力】

- `Item.deletedAt`、回收站、恢复和到期清理的生命周期范式；
- 已验收的 `MethodApplicationContextResult` 断裂状态机制；
- `MethodApplication.methodId + methodVersion` 的结构化使用事实；
- `MethodEvidence.methodId + reviewId` 的结构化证据事实；
- `MethodVersion.sourceReviewId` 的形成 / 修订来源事实；

## 【风险与保护策略】

1. **软删除不是断裂**：方法回收站状态必须显式返回，不能被当作 P1 异常。
2. **墓碑不是副本**：禁止把步骤、适用情况或版本正文复制进墓碑。
3. **证据关系不能靠推断**：墓碑版本来源索引是形成 / 修订关系的唯一可靠依据。
4. **事务原子性**：墓碑写入与方法 / 版本删除必须原子完成；事项清理与墓碑来源去悬空也必须原子完成。
5. **备份严格性**：新增墓碑后扩展目标集合，不允许放松 Review、Item 或版本引用校验。
6. **恢复语义**：恢复仅适用于回收站 `Method`；永久清理后的墓碑永不恢复方法正文。
7. **搜索隔离**：正常搜索和选择器必须排除回收站方法与墓碑；回收站内局部检索不是本期必要能力。

## 【测试建议】

### 自动化

1. 移入回收站后，正常方法列表、全局搜索、行动发起和验证 / 修订候选均排除；
2. `getContextForItem()` 分别返回 `available`、`method-in-trash`、`method-purged` 与既有 `unavailable`；
3. 回收站恢复后，方法、版本、证据和应用关系完整恢复为可用状态；
4. 到期清理创建的墓碑仅有允许字段，并删除方法与版本正文；
5. `MethodApplication` 保留原方法 ID 与实际版本，且被墓碑 `versions` 校验；
6. `MethodEvidence` 可在墓碑存在时可靠表达 formation / validation / revision；
7. 清理来源事项 / 复盘时，活跃版本与墓碑版本来源均不保留悬空 `sourceReviewId`；
8. 无剩余证据和应用的墓碑被清理；
9. v2 导出—新库导入—再次导出数据一致；
10. v1 导入兼容，v1 的必填关系断裂仍拒绝；
11. 事务中人为失败时，无部分墓碑、部分方法删除或部分来源清理。

### 人工 UAT（后端契约通过后）

- 方法详情页 `更多操作 → 移入回收站 → 二次确认`；
- 统一回收站的 `全部 / 事项 / 方法` 筛选、剩余时间、恢复；
- 复盘与历史详情的“已移入回收站 / 已永久清理”展示；
- 两种状态均不能发起行动、验证或修订；
- 全局搜索、流转历史抽屉、确认层之间的层级与关闭行为；
- 软删除、恢复、到期清理前后完整备份恢复。

## 【交付给研发的技术约束】

- 本文仍不授权写业务代码，须先经产品经理确认技术冻结与验收标准；
- UI 不得直接访问 Dexie 或自行合并墓碑关系；
- 所有命令必须通过 Application / Repository；
- 不得新增“删除方法即删除历史复盘”的语义；
- 不得将墓碑做成可编辑、可搜索、可复用或可恢复完整正文的对象；
- 不得按名称、时间、当前版本或文本匹配重建历史关系；
- 不得因 v2 兼容而放松必填关系校验；
- 若实现中发现既有数据无法构造满足上述不变量的墓碑，必须停止并上报架构师。
