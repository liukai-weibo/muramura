# 想试试事项渐进补充说明 — 轻量技术评审与实施约束

> 状态：**技术评审通过；先实施最小 Application / Repository 契约与自动化测试，前端等待契约通过后实施。**
> 范围：仅允许用户在 `idea_to_try`（想试试）事项详情中按需补充或编辑既有 `Item.content`。
> 非目标：不新增字段、Todo、第一步、日期、计划、提醒、标签、自动保存或状态事件。

## 【技术结论：可行】

该需求是对既有持久化字段 `Item.content` 的最小更新能力补齐，不改变事项状态机、复盘、方法、证据、备份对象或关系语义。

需要新增一个明确、受状态保护的 Application / Repository 写入契约。前端不得直接更新 IndexedDB，也不能将内容更新混入状态迁移。

## 【可复用现有能力】

- `Item.content` 已存在于 Contracts、IndexedDB、完整 JSON 备份导出与恢复；
- `Item.updatedAt` 已存在，`ItemApplicationService.listItems()` 已按其倒序排序；
- 当前 `create()` 对内容采用 `trim()` 归一化；
- `getItem()` 已将不存在和回收站事项稳定表达为“事项不存在”；
- 搜索在调用时直接查询 `Item.title` 与 `Item.content`，不存在独立持久化搜索索引；
- `changeStatus()` 已证明事项写入与状态事件可保持分离。

## 【最小新增能力】

### 1. Contracts

新增专用输入与 Repository 命令：

```ts
interface UpdateItemContentInput {
  content: string
}

interface ItemRepository {
  // 既有成员不变
  updateContent(id: string, input: UpdateItemContentInput): Promise<Item>
}
```

允许使用等价的 `updateContent(id: string, content: string)` 形状；关键不是参数包装方式，而是职责只能更新 `content` 与 `updatedAt`。

禁止将其泛化为 `updateItem()`：本期没有标题、状态、日期、标签或其他字段的编辑需求。预建通用更新入口会扩大后续写入边界。

### 2. Repository

`IndexedDbItemRepository.updateContent()` 的冻结规则：

```text
读取 Item
→ 不存在或 deletedAt 存在：抛出“事项不存在”
→ status !== idea_to_try：抛出“仅可为想试试事项补充说明”
→ content 执行 trim() 归一化
→ 仅写 content 与 updatedAt
→ 返回写入后的完整 Item
```

约束：

- 空字符串合法：代表用户主动清空既有补充说明；
- 不新增 `ItemStatusEvent`；
- 不修改 `createdAt`、标题、状态、关联、复盘或方法应用；
- 不需要多表事务；单条 `items.put()` 是本操作的完整原子边界；
- Repository 必须再次检查状态，不能只信任前端“当前仍是想试试”的页面判断。

### 3. Application

在 `ItemApplicationService` 新增：

```ts
updateItemContent(id: string, content: string): Promise<Item>
```

Application 仅转发到受保护的 Repository 契约；不得自动保存、不得在状态迁移时偷偷提交草稿、不得创建状态事件。

## 【数据可信边界】

### 可编辑对象

仅满足以下全部条件的事项可保存：

```text
事项存在
+ 未在回收站
+ status === idea_to_try
```

前端可以据此决定是否显示编辑入口；但这是体验层保护，最终真值仍由 Repository 写入时校验。

### 失败行为

| 条件 | Application / Repository 结果 | 前端行为 |
|---|---|---|
| 事项不存在 | 拒绝：`事项不存在` | 保留补充说明草稿，提示失败，并刷新 / 回到稳定对象状态 |
| 事项已移入回收站 | 拒绝：`事项不存在` | 保留草稿；不得写入回收站对象 |
| 事项已开始执行或变为其他状态 | 拒绝：`仅可为想试试事项补充说明` | 保留草稿；提示该事项状态已变化；不自动回写或自动保存 |
| 存储写入失败 | 透出稳定失败 | 保留草稿，允许重试 |
| 内容为空 | 成功保存空字符串 | 更新详情与搜索事实 |

“保存失败保留页面草稿”是前端状态责任；数据层不能保存半成品，也不能回退为自动保存。

### 与开始执行的并行关系

补充说明不是开始执行的前置条件：

```text
用户可直接开始执行
→ 不要求先保存说明
→ 未显式保存的草稿不写入
```

若用户在编辑期间主动开始执行：

- 前端不得阻断状态迁移；
- 未保存说明不应被自动提交；
- 此后点击保存由 Repository 拒绝，并保留草稿；
- 前端可提示“事项已不处于想试试，未保存说明未写入”。

这保证“行动优先”，同时避免把只允许在想试试阶段补充的内容写入执行中事项。

## 【读模型、刷新与异步保护】

### 成功保存后

Repository 返回更新后的 `Item`，前端应将其作为唯一可信结果：

1. 更新当前详情的 `selectedItem`；
2. 刷新或以返回对象替换本地事项列表项；
3. 由于 `updatedAt` 改变，列表若按更新时间排序，应重新按当前既有排序规则排序或调用现有 `listItems()` 刷新；
4. 保持以稳定 `selectedId` 选中当前事项，禁止因排序变化误选其他事项；
5. 清空“未保存草稿”标记，仅在写入成功后关闭编辑态或回到只读态。

### 搜索

现有搜索每次调用都直接查询 `Item.content`，无独立索引或缓存失效机制：

- 正常情况下，不需要新增搜索刷新 API 或索引；
- 若当前全局搜索浮层正显示同一查询的旧结果，前端在保存成功后应重新执行当前查询，或明确关闭该结果层；不得继续展示已过期 excerpt；
- 搜索未打开时无需预刷新。

### 失败与竞态

- 以事项 ID 绑定草稿，切换事项时不允许 A 事项异步保存结果覆盖 B 事项详情；
- 保存中切换事项时，返回结果只可更新仍对应同一 ID 的本地记录；
- 失败时草稿保留在对应事项 ID，不得被列表刷新、详情重拉或状态变化静默清空；
- 不引入自动保存、全局草稿库或跨会话持久化草稿。

## 【是否涉及 Schema / Migration / 备份】

| 边界 | 结论 |
|---|---|
| Item 状态机 | 不涉及 |
| Contracts | **涉及：最小更新命令** |
| Application | **涉及：最小更新门面** |
| Repository | **涉及：受状态保护的单字段写入** |
| IndexedDB Schema | 不涉及 |
| Dexie Migration | 不涉及 |
| JSON 备份结构 | 不涉及 |
| JSON 备份语义 | 可直接复用：`content` 本已完整导出 / 恢复 |
| 方法、复盘、证据、应用关系 | 不涉及 |
| 状态事件 | 不涉及 |

`updatedAt` 变化属于现有 `Item` 语义，不构成新增备份格式或 Migration。

## 【自动化测试建议】

### Application / Repository

1. `idea_to_try` 事项可写入非空补充说明，并返回更新后的 `content` 与更晚的 `updatedAt`；
2. 可显式保存空内容以清空说明；
3. 不存在事项写入被拒绝，错误稳定为“事项不存在”；
4. 已删除事项写入被拒绝，错误稳定为“事项不存在”；
5. 每个非 `idea_to_try` 状态均被拒绝，且内容、`updatedAt`、状态事件均不变化；
6. 成功写入不新增或变更 `ItemStatusEvent`；
7. 成功写入不改变标题、状态、创建时间、复盘、方法应用及关联；
8. 导出后恢复，更新后的 `content` 与 `updatedAt` 均保持；
9. 搜索可命中更新后的内容，不再命中被清空的旧内容；
10. 原有 Item 状态迁移、回收站、备份恢复回归继续通过。

### 前端（数据契约通过后）

1. 仅 `idea_to_try` 详情出现编辑入口；
2. 显式保存才调用更新命令；取消不调用；
3. 保存成功更新详情、列表排序和已打开搜索结果；
4. 保存失败、状态已变化、对象删除 / 不存在时保留草稿；
5. 编辑不阻断开始执行；开始执行不会自动保存草稿；
6. 异步返回不会覆盖已切换事项的详情或草稿。
