# 启动动作快照 — 正式实施任务书

> 状态：**产品已冻结；授权 Application / Repository 工程师先实施数据层与自动化测试。前端不得先实现持久化。**
> 关联评审：`docs/archive/architecture/start-action-snapshot/启动动作快照-技术评审.md`。
> 前置条件：Item Repository 并发一致性 P0 已关闭。

## 【技术结论：可行】

实现一个不可编辑的 `startAction` 历史快照：用户首次由 `idea_to_try` 进入 `doing` 时可选写入；有输入时，启动动作、状态迁移和状态事件必须同事务原子提交；无输入时，仍可正常开始执行但不写入字段。

该能力不引入 Todo、子任务、下一步、计划、进度、完成勾选、自动保存或后续编辑能力。

## 【一、冻结的业务语义】

```text
启动动作
= 用户首次从“想试试”进入“正在执行”时，
  为自己确定的最小行动锚点快照。
```

它不是：

```text
当前待办
下一步清单
执行进度
完成凭证
可持续维护的计划
复盘事实
方法步骤
```

生命周期：

```text
idea_to_try → doing
→ 可选写入一次 startAction
→ 后续只读保留

paused → doing
→ 仅恢复执行
→ 不创建、不替换、不覆盖 startAction
```

## 【二、Contracts】

### Item

新增可选字段：

```ts
interface Item {
  // existing fields
  startAction?: string
}
```

字段规则：

| 输入 | 持久化值 | 语义 |
|---|---|---|
| `undefined`、空字符串或仅空白 | 字段缺失（`undefined`） | 用户直接开始，未设置启动动作 |
| 非空文本 | `trim()` 后文本 | 可展示的首次启动快照 |

### 长度规则

**本期不新增独立的持久化最大长度。**

理由：现有 `Item.content` 没有长度上限；产品尚未提供真实“过长启动动作”摩擦证据。为此预设截断或字段限制会引入未验证业务规则，并可能静默损失用户明确输入。

因此冻结为：

```text
Repository：只 trim，不截断、不静默裁剪
前端：使用单条轻量输入控件；视觉截断仅是展示，不改变持久化文本
```

若 UI 需要输入框的体验性 `maxlength`，必须由产品单独给出明确值与“超长输入如何反馈”的验收标准；不得由前端自行限制。

### 启动输入与 Repository 命令

新增：

```ts
export interface StartItemExecutionInput {
  startAction?: string
}

export interface ItemRepository {
  // existing members
  startExecution(id: string, input?: StartItemExecutionInput): Promise<Item>
}
```

禁止新增：

```text
updateStartAction
replaceStartAction
clearStartAction
completeStartAction
appendStartAction
startActions[]
通用 updateItem
```

## 【三、Application 契约】

在 `ItemApplicationService` 新增：

```ts
startExecution(id: string, startAction?: string): Promise<Item>
```

固定职责：

```text
有非空启动动作
→ 调用 repository.startExecution(id, { startAction })

无启动动作
→ 调用 repository.startExecution(id)
```

Application 不得：

- 先调用 `changeStatus(id, 'doing')`，再保存启动动作；
- 在状态迁移成功后以第二个写入补填 `startAction`；
- 自动重试；
- 将启动确认层临时草稿写入任何持久化位置。

现有普通状态迁移接口继续保留：

```ts
changeStatus(id, status)
```

但 UI 从 `idea_to_try` 开始执行时必须调用 `startExecution()`，不能调用通用 `changeStatus()`。

## 【四、Repository 原子写入】

`IndexedDbItemRepository.startExecution()` 必须在同一个：

```text
readwrite(items, itemStatusEvents) transaction
```

内完成以下顺序：

```text
items.get(id)（必须在 transaction 内）
→ 不存在或 deletedAt 存在：throw “事项不存在”
→ current.status !== idea_to_try：执行既有状态机拒绝语义
→ assertTransition(current.status, doing)
→ current.startAction 已存在：throw “启动动作已存在，不能重写”
→ normalize input.startAction：trim，空值为 undefined
→ items.put({
    ...current,
    status: doing,
    ...(startAction ? { startAction } : {}),
    updatedAt: now,
  })
→ itemStatusEvents.add({
    itemId: id,
    fromStatus: idea_to_try,
    toStatus: doing,
    createdAt: now,
  })
→ return updated Item
```

### 原子不变量

```text
非空 startAction
+ idea_to_try → doing
+ 唯一 ItemStatusEvent
→ 必须同时成功或同时回滚
```

| 失败点 | 不得留下 |
|---|---|
| `items.put()` 失败 | 状态事件、startAction、doing 状态 |
| `itemStatusEvents.add()` 失败 | doing 状态、startAction |
| 校验失败 | 任意 Item 字段或状态事件变更 |

不得在 transaction 外读取旧 Item。必须复用 P0 已关闭的事务内重新读取模式，避免旧快照覆盖 `content`、`deletedAt` 或并发状态。

## 【五、失败重试与“不保存直接开始”】

### 正常启动确认层

正常态只有：

```text
取消 / 开始推进
```

- 输入可选；
- 用户点击“开始推进”：
  - 输入非空：调用 `startExecution(id, input)`；
  - 无输入：调用 `startExecution(id)`；
- 取消：只关闭确认层，不写入任何数据。

### 非空输入的原子保存失败后

仅当用户输入过非空启动动作且 `startExecution(id, input)` 失败时，前端可以显示：

```text
重试保存
不保存，直接开始
```

#### A. 重试保存

```text
保留原输入
→ 再次调用 startExecution(id, input)
```

不能使用缓存的旧 Item，不能先改状态。

#### B. 不保存，直接开始

```text
明确丢弃临时输入
→ 调用现有 itemApplication.changeStatus(id, 'doing')
→ 成功后不写 startAction
→ 关闭确认层并显示已开始推进
```

这是唯一允许使用普通 `changeStatus()` 进入 `doing` 的 UI 分支：用户已经明确选择不保存启动动作。该调用仍在 `rw(items, itemStatusEvents)` 中原子写入状态和事件。

如果“直接开始”也失败：

- 保持确认层；
- 不声称已开始；
- 不自动重试；
- 临时输入已被用户明确放弃，不得重新持久化或自动恢复为启动动作；
- 前端可作为纯 UI 草稿继续保留该文本，供用户自行决定是否再次输入，不能把它当作已保存事实。

### 特殊失败的前端语义

| 失败 | 前端处理 |
|---|---|
| `事项不存在` | 保留输入；提示事项已不可用；不得进入 doing |
| 状态已变化 / 状态机拒绝 | 保留输入；刷新当前事项；不得覆盖新状态 |
| `启动动作已存在，不能重写` | 不得提供覆盖入口；刷新事项并展示已有只读快照 |
| 存储异常 | 保留输入；允许重试或明确不保存直接开始 |

## 【六、状态、历史与只读展示约束】

| 场景 | 是否展示 | 规则 |
|---|---|---|
| `idea_to_try` | 否 | 尚未执行；不显示空占位 |
| `idea_later` | 否 | 尚未执行；不显示空占位 |
| `doing` | 是（有值时） | 轻量行动锚点，低于补充说明，高于操作按钮 |
| `paused` | 是（有值时） | 只读，用于恢复上下文 |
| `waiting_review` | 是（有值时） | 低于待复盘任务与复盘入口 |
| `reviewed` | 是（有值时） | 低于复盘事实、方法证据、状态历史 |
| `archived_no_review` | 是（有值时） | 低于归档状态与流转历史 |
| `abandoned` | 是（有值时） | 低于放弃决策与流转历史 |
| 回收站 | 是（有值时） | 只读，无编辑、完成、替换或操作入口 |

前端禁止将启动动作展示为：

```text
待办复选框
当前下一步
完成状态
进度条
复盘已完成事实
可编辑输入框
```

## 【七、备份、恢复与旧数据】

### IndexedDB

不改 Schema、Dexie version 或 Migration：

- `startAction` 是 `Item` 上未索引的可选字段；
- 不按它搜索、筛选、排序、统计；
- 旧本地 Item 缺失字段即为无启动动作。

### JSON 备份

不新增集合、不升级 `BackupDocument.version`。

但在 `BackupApplicationService.parseAndValidate()` 中补充：

```text
若 Item.startAction 存在
→ 必须是 string

缺失
→ 合法，按 undefined 处理
```

导出与恢复：

```text
有值 → 作为 Item 原样导出与恢复
无值 → 不伪造空字符串
旧备份缺字段 → 正常恢复，无启动动作
```

不得利用导入时的状态或历史事件自动补填启动动作；历史无法可靠还原时就是缺失。

## 【八、自动化测试】

### 数据层

1. `idea_to_try → doing` + 非空输入：写入 trim 后 `startAction`、状态和唯一事件；
2. 无输入、空字符串、纯空白：进入 doing，但字段为 `undefined`；
3. `items.put()` 失败：不写事件、不留 `startAction`、状态不变；
4. `itemStatusEvents.add()` 失败：状态和 `startAction` 一起回滚；
5. 不存在 / 回收站事项：拒绝 `事项不存在`，无事件；
6. `idea_later`、`doing`、`paused` 等非 `idea_to_try` 调用 `startExecution()`：被状态机拒绝，不生成或覆盖快照；
7. 已有 `startAction` 的异常 / 导入数据不能被专用命令覆盖；
8. `paused → doing` 走普通 `changeStatus()` 后保留原快照，且不产生第二条启动快照；
9. 内容编辑、删除、恢复及 purge / restore 交错不回滚或伪造 `startAction`；
10. 完成复盘、形成 / 验证 / 修订方法后，启动动作不进入 Review 或方法关系；
11. 导出 v2 完整备份 → 解析 → 新库恢复后，快照、状态和状态事件一致；
12. 旧备份缺 `startAction` 可恢复；非 string `startAction` 被拒绝；
13. 既有 Item P0、回收站、备份恢复、复盘、方法生命周期全量回归。

## 【交付给研发的技术约束】

1. 有输入时必须走 `startExecution()`，不能拆成两个写入；
2. 无输入时也建议走 `startExecution()`，统一首次启动路径；
3. 只有失败后的用户明确选择“不要保存”才允许走 `changeStatus(id, 'doing')`；
4. 不得将启动动作写入 `Item.content`、Review、方法或状态事件；
5. 不得追加后续编辑能力；
6. 不得因旧数据缺失字段而推断或回填启动动作；
7. 必须复用事务内最新读取，不得回退 Item P0 修复；
8. 数据层自动化和 QA 通过前，前端不得实现持久化或详情展示。
