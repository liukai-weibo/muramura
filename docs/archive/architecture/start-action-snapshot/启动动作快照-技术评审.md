# 启动动作快照 — 轻量技术评审

> 状态：**有条件可行；不允许开发，待产品确认本评审中的两个写入语义后冻结。**
> 范围：用户从 `idea_to_try` 首次进入 `doing` 时，可选写入一条不可编辑的“启动动作”历史快照；后续详情只读展示。
> 非目标：Todo、子任务、计划、进度、完成勾选、下一步、提醒、自动保存、编辑 / 替换 / 追加启动动作。

## 【技术结论：有条件可行】

产品判断成立：若“去菜市场买个菜”仅在启动确认层短暂出现、成功后消失，它不构成稳定的行动锚点；将其作为首次进入执行时的只读快照持久化，可以保留真实的行动转换上下文。

但它是新增的 `Item` 持久化事实，并且必须与：

```text
idea_to_try → doing
```

在同一可信事务内完成。因此不能由前端在状态迁移成功后再单独保存，也不能复用现有自由内容编辑能力。

推荐实现为可选字段与专用命令：

```ts
interface Item {
  // existing fields
  startAction?: string
}

interface StartItemExecutionInput {
  startAction?: string
}
```

```text
ItemApplicationService.startExecution(itemId, input)
→ Repository 在一个 rw(items, itemStatusEvents) transaction 内
→ 重读当前 Item
→ 校验当前状态是 idea_to_try
→ 可选写入 startAction
→ 写入 doing
→ 写入唯一状态事件 idea_to_try → doing
→ 返回更新后的 Item
```

不建议把 `startAction` 挂进通用 `changeStatus()` 参数：该字段只在这一条特定业务转换有意义；泛化会允许 `paused → doing`、`doing → waiting_review` 等无关路径误传“启动动作”。

## 【一、概念与数据语义】

### 字段定义

```ts
interface Item {
  id: string
  title: string
  content: string
  startAction?: string
  status: ItemStatus
  createdAt: string
  updatedAt: string
  deletedAt?: string
}
```

`startAction` 的唯一语义：

```text
用户首次从 idea_to_try 进入 doing 时，
当时为该事项确定的最小启动行动。
```

它不是：

```text
当前下一步
待办项
可完成项
进度
执行事实
暂停 / 放弃原因
复盘内容
方法步骤
```

### 写入规则

| 情形 | 行为 |
|---|---|
| 从 `idea_to_try` 开始执行，输入非空文本 | `trim()` 后写入快照 |
| 从 `idea_to_try` 直接开始，未输入或仅空白 | 不写字段，保持 `undefined` |
| `paused → doing` 恢复 | 必须使用既有 `changeStatus()`；不得写入或修改快照 |
| 任何后续状态迁移 | 不得写入或修改快照 |
| 任何详情编辑 | 无更新契约、无编辑入口 |
| 已有快照的异常 / 导入数据再次调用专用命令 | 不得覆盖；明确拒绝“启动动作已存在，不能重写” |

快照写入后不可变。`updateItemContent()` 不得触及它。

## 【二、最小 Contracts / Application / Repository 契约】

### Contracts

新增：

```ts
export interface StartItemExecutionInput {
  startAction?: string
}

export interface Item {
  // existing members
  startAction?: string
}

export interface ItemRepository {
  // existing members remain unchanged
  startExecution(id: string, input?: StartItemExecutionInput): Promise<Item>
}
```

保留：

```ts
changeStatus(id, status)
```

但前端“从想试试开始执行”的唯一调用改为 `startExecution()`；其他状态迁移继续使用 `changeStatus()`。

禁止：

```text
updateItem()
updateStartAction()
replaceStartAction()
completeStartAction()
appendStartAction()
任意数组 / 子对象形式的行动步骤
```

### Application

新增：

```ts
ItemApplicationService.startExecution(id: string, startAction?: string): Promise<Item>
```

Application 不应先调用 `changeStatus()` 再调用其他写入；只允许调用 Repository 专用命令。

### Repository

新增 `startExecution()`，固定事务顺序：

```text
transaction(rw, items, itemStatusEvents)
→ transaction 内 items.get(id)
→ 不存在或 deletedAt：事项不存在
→ current.status !== idea_to_try：沿用状态机拒绝语义
→ assertTransition(idea_to_try, doing)
→ 若 current.startAction 已存在：拒绝，禁止覆盖
→ normalize input.startAction：trim 后非空才写字段
→ items.put({ ...current, status: doing, startAction?, updatedAt })
→ itemStatusEvents.add({ fromStatus: idea_to_try, toStatus: doing })
→ 返回 Item
```

`startAction` 空输入不写成空字符串：

```text
undefined = 用户直接开始，未设置启动动作
非空文本 = 可展示启动快照
```

这是展示与备份的稳定降级边界。

## 【三、状态、复盘、方法与回收站兼容性】

### 状态机

- 不修改 `ItemStatus` 枚举；
- 不修改现有转换规则；
- 只为既有合法转换 `idea_to_try → doing` 提供专用原子编排；
- `paused → doing` 仍是恢复，不是重新启动，不能产生第二条快照；
- 状态事件保持原有单条事件，不为启动动作新增事件类型。

### 复盘与方法

`startAction` 不进入：

```text
Review
Method
MethodVersion
MethodEvidence
MethodApplication
ItemLink
```

在 `waiting_review`、`reviewed`：

```text
复盘事实 / 方法证据
> 启动动作（低优先级历史上下文）
```

启动动作绝不能被展示为“已完成的事实”，也不能预填复盘字段。

### 归档、放弃与回收站

| 状态 | 展示规则 |
|---|---|
| `idea_to_try` / `idea_later` | 不展示：正常数据不应有快照 |
| `doing` | 展示为低强调行动锚点 |
| `paused` | 保留只读，帮助恢复上下文 |
| `waiting_review` / `reviewed` | 保留只读，低于复盘事实 |
| `archived_no_review` / `abandoned` | 保留只读，低于状态决策与历史 |
| 回收站 | 有值则只读展示；无编辑或操作 |

项目事实边界：正常状态机不应使 `idea_later` 或 `idea_to_try` 存在 `startAction`。若导入旧 / 外部数据发生此组合，前端不得据此推断“已经开始执行”；只在 `doing` 及其后续状态展示。

## 【四、IndexedDB Schema、Migration 与备份】

### IndexedDB Schema / Migration

**不需要新增 Dexie 索引或升级 Schema。**

理由：

- `startAction` 是可选、未索引的 `Item` 对象字段；
- 当前 items store 以对象整体存储，读取按 ID；
- 不需要按启动动作筛选、搜索、排序或统计；
- 现有对象缺失该字段即代表无启动动作，稳定兼容。

因此：

```text
Dexie version：不变
Migration：不需要
```

不得为“未来可能分析”提前建立索引、统计表或第二个行动对象。

### JSON 备份

`Item` 已是完整备份对象的一部分。新增可选字段会自然进入 JSON 导出和恢复。

结论：

| 边界 | 结论 |
|---|---|
| BackupData 新集合 | 不需要 |
| BackupDocument version | 不升级 |
| v1 / v2 兼容 | 现有备份缺失 `startAction` 即视为 `undefined` |
| 导入校验 | 若字段存在，必须是 string；缺失允许 |
| 导出 | 有值则原样导出；无值不应伪造空字符串 |

虽然不升级备份版本，但必须补充解析校验与导出—恢复测试，因为备份中的 `Item` 业务语义增加了一个可选持久化事实。

## 【五、P0 一致性与异步保护】

已关闭的 Item Repository P0 修复是本需求前置条件。`startExecution()` 必须复用同样的事务模式：

```text
事务内重新读取当前 Item
→ 合并 status / startAction / updatedAt
→ 与 ItemStatusEvent 原子写入
```

禁止：

```text
前端先 changeStatus(doing)
→ 再 update startAction

前端先存草稿
→ 状态成功后另一次 items.put

在 transaction 外 getById
→ 用旧 Item 合成并 put
```

失败时：

- Item 状态与 `startAction` 都不得部分写入；
- 状态事件不得单独写入；
- 前端保留用户输入的启动动作草稿，允许用户重新提交或直接开始；
- 用户切换事项或旧请求返回时，不得覆盖另一事项的确认层草稿。

## 【六、自动化测试】

最低自动化覆盖：

1. `idea_to_try → doing` 带非空启动动作：
   - 状态变为 `doing`；
   - `startAction` 被 trim 并持久化；
   - `updatedAt` 更新；
   - 唯一状态事件为 `idea_to_try → doing`；
2. 直接开始或空白输入：
   - 状态变为 `doing`；
   - `startAction` 为 `undefined`，不为 `''`；
3. 写入与状态事件原子性：
   - `items.put()` 失败时不写事件；
   - `itemStatusEvents.add()` 失败时状态与启动动作回滚；
4. 已删除 / 不存在事项：拒绝 `事项不存在`，不产生事件；
5. 非 `idea_to_try` 调用专用命令：拒绝，且不新增 / 覆盖快照；
6. `paused → doing` 使用普通状态迁移后，既有启动动作不变；
7. 已有启动动作不得通过专用命令覆盖；
8. 删除 / 恢复保留启动动作；回收站读取只读可见；
9. 到期永久清理后，事项与启动动作一并删除，备份引用完整性继续通过；
10. JSON 导出 → 解析 → 新库恢复后，`startAction` 与状态事件保持；旧备份缺字段可恢复；
11. `waiting_review` / `reviewed` 完成复盘后，Review、方法、证据、应用与启动动作互不改写；
12. 既有 Item P0：内容—状态、删除—恢复、purge—restore 交错及 `completeReview()` 原子性全量回归。
