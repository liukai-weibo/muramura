# 补充说明可写状态范围扩展 — 轻量技术评审

> 状态：**有条件可行；不允许开发，待产品澄清状态枚举后冻结。**
> 范围：将既有 `ItemApplicationService.updateItemContent(itemId, content)` 从仅 `idea_to_try` 可写，扩展为全部未删除事项可写；回收站继续只读。
> 非目标：不改变补充说明的业务含义；不新增字段、状态事件、状态机、复盘、方法关系、Schema、Migration 或备份格式。

## 【技术结论：有条件可行】

技术上，这是对现有单字段写入守卫的最小放宽：从“未删除且 `idea_to_try`”改为“未删除”。不需要新增 Contracts、Application 命令、数据表、备份集合或读模型。

但当前产品描述存在一个必须先澄清的状态枚举冲突，不能直接开发：

```text
当前真实 ItemStatus：
idea_to_try
idea_later
doing
paused
waiting_review
reviewed
archived_no_review
abandoned

产品列举：
idea_to_try
idea_later
in_progress（当前不存在）
paused
waiting_review
reviewed
abandoned
```

产品同时使用“所有未删除事项”与“列出的七种状态”两种范围：前者应包含 `archived_no_review`，后者遗漏该状态；`in_progress` 也不是当前状态机枚举。

在产品确认前，架构不允许实现方自行将 `in_progress` 映射为 `doing`，或自行决定 `archived_no_review` 是否可写。

## 【一、Contracts、Application、Repository 最小范围】

### Contracts

**不需要修改。**

现有专用契约已足够：

```ts
interface UpdateItemContentInput {
  content: string
}

interface ItemRepository {
  updateContent(id: string, input: UpdateItemContentInput): Promise<Item>
}
```

不应将其扩展为通用 `updateItem()`；本轮只调整既有 `updateContent()` 的可写对象范围。

### Application

**不需要修改。**

现有入口保持：

```ts
ItemApplicationService.updateItemContent(id: string, content: string): Promise<Item>
```

Application 仍只转发专用内容更新命令，不能变成状态变更、复盘更新或自动保存入口。

### Repository

**需要最小修改。**

将现有写入守卫：

```text
不存在或 deletedAt 存在 → 事项不存在
status !== idea_to_try → 仅可为想试试事项补充说明
```

改为：

```text
不存在或 deletedAt 存在 → 事项不存在
否则 → trim content，仅写 content 与 updatedAt
```

除删除状态外，不再按活跃状态拒绝更新。

建议同时将该操作收敛到一个 `items` 的读写事务中：

```text
transaction(rw, items)
→ 在事务内读取当前 Item
→ 校验 Item 存在且未 deletedAt
→ 写入 content / updatedAt
→ 返回更新后的 Item
```

原因不是增加新并发机制，而是让“回收站不可写”的判断与 `put` 保持同一可信写入边界，避免多标签页或异步操作间的读后写窗口。

## 【二、复盘、证据、状态历史与搜索兼容性】

### `waiting_review`、`reviewed`、`abandoned`

兼容，前提是产品已冻结的内容语义不变：

```text
补充说明 = 事项背景、范围、为什么值得做
```

`content` 并不承载：

```text
复盘事实
执行进度
暂停 / 放弃原因
方法步骤
状态迁移事实
```

因此，更新 `content` 不会也不得：

- 更新或删除 `Review`；
- 新增或修改 `MethodEvidence`、`MethodVersion`、`MethodApplication`；
- 创建或修改 `ItemStatusEvent`；
- 改变事项状态或触发重新复盘。

对 `waiting_review`、`reviewed`、`abandoned` 的影响仅是事项背景文本更新；历史与复盘继续是更高优先级的事实层。前端必须以信息层级保障此点，不能把补充说明排在复盘事实或流转历史之上。

### 搜索

兼容。现有搜索直接查询 `Item.title` 与 `Item.content`，没有独立索引：

- 保存成功后，新内容可自然被搜索命中；
- 清空后旧关键词不再命中；
- 若搜索结果浮层已打开，前端应按既有约束刷新当前查询或关闭旧结果层。

### 列表与详情

兼容。`updatedAt` 更新会触发现有事项列表重排。所有活跃状态放开编辑后，已复盘 / 已放弃事项也可能因补充说明保存而向列表前部移动。

这是现有“按 `updatedAt` 倒序”读模型的自然结果，不是数据错误。产品应确认接受该呈现影响；若不接受，需要另立“列表排序语义”范围，不能在本需求中私自绕开 `updatedAt`。

## 【三、已删除或不存在事项的稳定失败】

冻结为：

| 条件 | Repository 结果 | 前端处理 |
|---|---|---|
| 事项不存在 | 抛出 `事项不存在` | 保留该 itemId 草稿，提示失败 |
| `deletedAt` 存在 | 抛出 `事项不存在` | 保留草稿；回收站只读，不显示编辑入口 |
| 写入存储失败 | 透出稳定失败 | 保留草稿，可显式重试 |

回收站使用“事项不存在”而不是暴露内部 `deletedAt` 细节，沿用既有 `getItem()` / 状态变更的稳定语义。

## 【四、并发与旧请求保护】

不需要为了本轮新增乐观锁、版本号字段、全局状态库或自动保存。

但必须保持以下最小保护：

### 数据层

- 在单个 `items` 读写事务中重新读取并确认事项未删除；
- 内容更新只写 `content / updatedAt`；
- 不将前端页面上一次读取到的状态作为写入授权。

### 前端

- 草稿以 `itemId` 隔离；
- 保存成功只更新对应 `itemId` 的本地项；
- 保存返回时若当前已切换到另一事项，不得改变另一事项编辑态或草稿；
- 保存失败不得清除草稿；
- 状态变化不再是内容保存的拒绝理由，但删除 / 移入回收站仍必须失败；
- 不自动保存、不用异步默认值覆盖用户输入。

本轮扩展后，“编辑中开始执行”不再需要通过失败来保护：只要事项未删除，用户后续显式保存仍可成功。这与产品确认的“所有未删除事项可编辑”一致。

## 【五、是否涉及 Schema / Migration / 备份】

| 边界 | 结论 |
|---|---|
| Contracts | 不涉及 |
| Application | 不涉及 |
| Repository | **涉及：仅修改现有状态写入守卫，并建议事务化读写** |
| IndexedDB Schema | 不涉及 |
| Dexie Migration | 不涉及 |
| JSON 备份格式 / 版本 | 不涉及 |
| JSON 备份语义 | 直接复用既有 `Item.content` 与 `updatedAt` |
| Item 状态机 | 不涉及 |
| ItemStatusEvent | 不涉及 |
| Review / Method / Evidence / Application | 不涉及 |

## 【六、自动化测试】

在产品澄清状态范围后，最低自动化范围：

1. 所有经产品确认的、未删除状态均可更新非空内容与显式清空；
2. 回收站事项更新被拒绝为 `事项不存在`；
3. 不存在事项更新被拒绝为 `事项不存在`；
4. 成功更新仅改变 `content` 与 `updatedAt`；
5. 成功与失败均不新增、不修改 `ItemStatusEvent`；
6. 成功更新不修改标题、状态、`createdAt`、Review、方法、版本、证据、方法应用和事项关系；
7. 更新后的内容在搜索中可命中；清空后旧关键词不再命中；
8. 导出、解析、恢复后，内容和 `updatedAt` 保持；
9. `waiting_review`、`reviewed`、`abandoned` 更新内容后，复盘及方法证据查询结果保持不变；
10. 删除 / 内容更新并发测试：当事务内读到 `deletedAt` 时必须拒绝且不改写回收站事项；
11. 原有状态迁移、回收站、复盘、方法生命周期及备份恢复全量回归通过。

## 【七、后续前端修改边界】

在 Repository 修改、自动化测试和 QA 验收通过后，前端允许：

```text
apps/client/src/pages/index/index.tsx
apps/client/src/pages/index/index.scss
前端相关测试
```

前端交互约束：

- 所有未删除事项详情可显示添加 / 编辑补充说明入口；
- 回收站只读；
- 在 `waiting_review`、`reviewed`、`abandoned` 中，补充说明必须低于复盘事实和状态历史；
- 显式保存 / 取消 / 空内容 / 失败保留 / itemId 草稿隔离继续保持；
- 不新增自动保存、第一步、Todo、日期、计划、提醒、标签或新的编辑字段；
- 不修改状态机、复盘或方法流程。

## 【交付给研发的技术约束】

- 先等待产品澄清 `doing` 与 `archived_no_review`；
- 未澄清前，不得实现“所有状态可写”；
- 澄清后仅修改 `IndexedDbItemRepository.updateContent()` 的状态守卫；
- 不新增 Contracts / Application 命令，不泛化为 `updateItem()`；
- 回收站与不存在事项继续稳定拒绝为 `事项不存在`；
- 只写 `content / updatedAt`，不写状态事件；
- 使用事务内重读保证删除状态不被旧读取覆盖；
- 后端 / Application / Repository 自动化与 QA 通过前，前端不得放开其他状态编辑入口。

```text
当前状态机没有 in_progress，实际状态为 doing。
```
