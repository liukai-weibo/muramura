# 探索主线 V1：最小架构评审与技术任务书

> 状态：**架构冻结完成；当前禁止编码。**
>
> 实施前置：当前 MySQL 快速接入 Sprint 必须先完成并封板其浏览器完整闭环、JSON 导出—清库—恢复、API / MySQL 重启验证及写入失败阻断复验。探索主线不得与该闭环或当前写入故障排查混合实施。

## 【技术结论：有条件可行】

探索主线 V1 是一个新的长期业务对象及 Item 的可信 `0..1` 结构化关系；必须由 MySQL Schema、Repository、Application 读模型和 API 共同表达。禁止以前端局部状态、标题、时间、文案、状态、计数或相似度推断关联。

当前运行事实保持：

```text
H5 → loopback API → Application → MySQL
MySQL 是当前 H5 运行数据源
IndexedDB 不参与当前 H5 业务读写
单一 MySQL Docker 容器（127.0.0.1:3306）
├─ knowledge_base：日常
└─ knowledge_base_uat：隔离 UAT
```

本 V1 不引入双写、同步、回填、浏览器直连 MySQL、子任务、进度、计划或自动化状态判断。

## 【最小 MySQL 模型与 Migration】

新增 migration `004_add_exploration_tracks.sql`；该 migration 必须在 `knowledge_base` 与 `knowledge_base_uat` 独立执行，继续使用既有 migrator 最小 DDL / DML 权限、checksum 与 advisory lock。

### 1. `exploration_tracks`

```sql
CREATE TABLE exploration_tracks (
  id VARCHAR(128) PRIMARY KEY,
  name VARCHAR(80) NOT NULL,
  normalized_name VARCHAR(80) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  updated_at DATETIME(3) NOT NULL,
  deleted_at DATETIME(3) NULL,
  UNIQUE KEY exploration_tracks_normalized_name_unique (normalized_name),
  KEY exploration_tracks_active_updated_idx (deleted_at, updated_at DESC)
) ENGINE=InnoDB;
```

### 2. Item 可选关联

```sql
ALTER TABLE items
  ADD COLUMN exploration_track_id VARCHAR(128) NULL,
  ADD KEY items_exploration_track_created_idx (exploration_track_id, created_at DESC),
  ADD CONSTRAINT items_exploration_track_fk
    FOREIGN KEY (exploration_track_id) REFERENCES exploration_tracks(id);
```

设计取舍：

- 关联字段置于 `items`，以数据库约束表达“一事项至多一主线”；不创建无业务价值的中间表。
- `NULL` 表示用户明确未关联或已移除关联；不允许前端以任何字段替代该事实。
- 外键允许 Item 指向软删除主线，因此删除主线不会破坏事项、Review、方法或状态事件。
- V1 不物理永久删除主线；主线软删除后保留关系和历史降级所需名称。主线的 30 天物理清理、墓碑或级联清理属于新范围，未经独立评审不得加入。
- migration 前的 Items 自动为 `exploration_track_id = NULL`；无历史迁移、回填或猜测。

### 3. Migration 预检、执行与回滚策略

- migration 前检查 `exploration_tracks` / `items.exploration_track_id` / 相关索引及外键不存在，防止半执行状态伪装为成功；沿用既有 migration runner checksum / schema 版本语义。
- MySQL DDL 不可一般性事务回滚，因此预检必须在 DDL 前完成；失败不得写入 `schema_migrations` 的 004 成功记录。
- 本地开发回滚只允许在未承载真实数据的临时库中按反向 DDL 重建；不得修改已执行 migration 文件、不得在日常库执行“撤销脚本”。

## 【Contracts、规范化与 Application 错误语义】

### 1. 新增 Contracts

```ts
interface ExplorationTrack {
  id: string
  name: string
  createdAt: string
  updatedAt: string
  deletedAt?: string
}

type ItemExplorationTrackContext =
  | { status: 'no-association'; itemId: string }
  | { status: 'available'; itemId: string; track: ExplorationTrack }
  | { status: 'track-deleted'; itemId: string; track: ExplorationTrack }
  | { status: 'unavailable'; itemId: string; trackId: string }
```

`unavailable` 只表达已存在的结构化外键无法取得对应记录的异常事实；它不是“无关联”，不得自动清空、重连或伪造名称。

创建事项时使用显式区分的可选输入：

```ts
type ExplorationTrackSelection =
  | { type: 'existing'; trackId: string }
  | { type: 'new'; name: string }

interface CaptureIdeaInput {
  // existing fields unchanged
  explorationTrack?: ExplorationTrackSelection
}
```

关联调整采用明确契约，而不是 `undefined` 的隐式语义：

```ts
assignItemToExplorationTrack(itemId: string, trackId: string)
removeItemFromExplorationTrack(itemId: string)
```

### 2. 名称规则

Application 负责规范化，Repository 不根据数据库 collation 猜测业务同名：

```text
显示名：Unicode NFKC → trim
规范化名：显示名 → lower-case
长度：按 Unicode code point 计，1 至 80
唯一性：normalized_name 在所有未物理删除记录中全局唯一，包含软删除主线
```

V1 选择“包含已删除主线的全局唯一”，以避免删除后创建同名主线、再恢复时产生不可裁决的名称冲突。删除不是释放名称；用户需要继续使用该主线时应恢复原主线。

稳定 Application 错误：

```text
主线名称不能为空
主线名称最多 80 个字符
已存在同名探索主线
探索主线不存在
探索主线已删除
事项不存在
```

数据库唯一键竞争必须映射为 `已存在同名探索主线`；不得泄露 SQL / driver 错误，API 映射为既有 `409 CONFLICT`。输入校验错误为 `400 VALIDATION_FAILED`，不存在 / 已删除的不可选主线为 `404 NOT_FOUND` 或已冻结业务冲突语义，必须在 API 矩阵中固定且保持一致。

## 【Repository、事务与可信写入】

新增 `ExplorationTrackRepository` 与一个专门承载跨对象写入的 `ExplorationTrackWorkflowRepository`；前端、API handler 和现有 Item Repository 均不得通过多次独立调用拼装原子性。

### 1. 主线自身写入

- create / rename：事务内规范化、锁定同 `normalized_name` 的候选记录或处理唯一键竞争，再创建 / 更新。
- soft delete：`SELECT ... FOR UPDATE` 锁定主线，仅写 `deleted_at` / `updated_at`；不修改关联 Items、Reviews、Methods、Links 或状态事件。
- restore：锁定主线并验证全局 normalized name 仍无冲突；仅清空 `deleted_at`。若未来发现违反唯一性的历史脏数据，明确拒绝、零副作用，不能改名或合并。

### 2. 创建事项并关联主线

`createItemWithExplorationTrack()` 是唯一允许“创建事项 + 已有主线关联”及“创建事项 + 创建主线 + 关联”的编排入口。必须在一个 MySQL transaction 内：

```text
已有主线：SELECT active exploration_track FOR UPDATE
新主线：规范化 → 同名检查 / 唯一竞争保护 → INSERT exploration_track
→ INSERT Item(exploration_track_id = actual track id)
→ INSERT 初始 ItemStatusEvent
→ COMMIT
```

任一步失败、初始状态事件失败或 commit 前连接中断，必须回滚 Track（如本次新建）、Item、关联字段与 Event。已有主线在失败时保持原样。

未选择主线的既有快速捕获仍走既有 Item 创建 Contract，行为不变。

### 3. 调整与移除关联

- assign：同一 transaction 内 `SELECT active Item FOR UPDATE`、`SELECT active Track FOR UPDATE`、更新 `items.exploration_track_id`。
- remove：锁定 active Item，将外键设为 `NULL`；不删除主线、不改写 Review / 方法 / Event。
- 不存在、已删除或已进回收站 Item / Track 均拒绝、零副作用。
- 同一 Item 并发调整时，最后提交的明确用户操作可成为最终关系；每个提交只基于 transaction 内锁定的最新 Item。前端不得以旧加载结果覆盖新选择。

## 【结构化读模型】

所有读模型由 Application 从 Repository 返回；前端不得自行 join 或补全。

```ts
interface ExplorationTrackListEntry {
  track: ExplorationTrack
  latestAssociatedItem?: { id: string; title: string; status: ItemStatus; createdAt: string }
}

interface ExplorationTrackHistoryEntry {
  item: { id: string; title: string; status: ItemStatus; createdAt: string }
  review?: { id: string; createdAt: string; actualAction: string; result: string }
}

interface ExplorationTrackHistory {
  track: ExplorationTrack
  activeHistory: ExplorationTrackHistoryEntry[]
  abandonedHistory: ExplorationTrackHistoryEntry[]
}
```

规则：

- 活跃主线列表只返回 `deleted_at IS NULL` 的主线；按 `updatedAt DESC, id ASC` 稳定排序。
- 可选主线列表仅返回活跃主线，按 `name` 规范化稳定排序；不根据历史关联次数排序。
- `latestAssociatedItem` 仅从未删除 Items 取 `created_at DESC, id ASC` 的最近一项；无项时省略，前端显示“暂无关联行动”。不得返回计数、进度或完成率。
- 历史按 Item `created_at DESC, id ASC` 排序；回收站 Items 不返回。
- `abandoned` Items 仅在 `abandonedHistory` 中返回，默认不混入主历史；不把其他状态归为“完成”或“失败”。
- 复盘摘要仅由真实 `reviews.item_id` 读取 `actualAction` / `result` 字段；无 Review 则没有摘要。读取异常或无法建立该结构化关系时返回明确可区分降级状态 / API 错误，前端显示“请在事项中查看”，不得拼接标题或文本伪造摘要。
- Item 详情关联使用 `ItemExplorationTrackContext`：软删除主线为 `track-deleted` 并显示“原探索主线已删除”；不得显示成未关联。
- “查看事项”只返回真实 `item.id` 与真实 `item.status`，由前端切回事项工作台并按 API 重新读取定位；不得用主线本地缓存猜测事项池。

## 【删除、恢复与缺失关联语义】

| 场景 | 冻结语义 |
|---|---|
| 删除主线 | 仅软删除主线。关联 Items、Reviews、方法和状态事件零改写。正常列表 / 选择器隐藏主线。 |
| 恢复主线 | 仅恢复主线；所有仍实际指向它且未删除的 Items 自动重新在读模型中可见。 |
| 删除关联 Item | 仅 Item 进入既有回收站；不显示于主线历史，主线不删除、不改名、不解除关系。 |
| 恢复关联 Item | 恢复其原 `exploration_track_id`；若主线 active，恢复到历史；若主线 deleted，Item 详情诚实显示已删除主线。 |
| 已放弃 Item | 留在 `abandonedHistory` 的按需展开区；不从数据库断开关系。 |
| 运行期外键缺失 | `unavailable`，不得自动置 NULL 或伪装成无关联；记录可诊断错误并限制该关联调整，待数据修复。 |
| 备份内断裂引用 | 严格拒绝恢复、零业务写入；不得为通过恢复删除 / 伪造关联。 |

V1 不把探索主线纳入既有 Item / Method 的 30 天物理 purge。主线保留软删除记录是关系可信降级的必要条件；任何永久清理策略须独立产品和架构评审。

## 【BackupData 与恢复策略】

探索主线新增第十个业务集合，因此新增 `BackupDocumentV3`：

```ts
interface BackupDataV3 extends BackupData {
  explorationTracks: ExplorationTrack[]
}
```

```text
旧 Backup v1 / v2 导入：将 explorationTracks 归一化为 []；所有旧 Items 的 explorationTrackId 视为缺失；不失败、不新增关系。
新 Backup v3：必须含 explorationTracks；Items 可选 explorationTrackId；导出 / 恢复保留 Track 名称、软删除、关联与 Item 原有事实。
```

严格校验：

- Track `id`、name、normalized name、时间与删除字段合法；重新执行同一规范化规则并要求等于导出 normalized name。
- Track id 与 normalized name 分别唯一。
- `item.explorationTrackId` 若存在，必须指向本备份中的 Track，允许指向软删除 Track。
- 不接受既有九集合引用、主线关联或版本数据的断裂、重复和不合法格式。

`replaceData()` 在单一 MySQL DML transaction 中：

```text
parseAndValidate() 完成
→ 清理既有业务集合（先依赖表与 Items，后 exploration_tracks）
→ 导入 exploration_tracks
→ 导入 Items（含 exploration_track_id）
→ 按既有顺序导入 Reviews / Methods / Versions / Evidence / Applications / Tombstones / Links / Events
→ COMMIT
```

任何末端失败回滚所有十个集合；`system_metadata` 继续不导出、不删除、不恢复、不覆盖。不得修改 v1 / v2 的既有 JSON 含义；V3 是显式版本演进。

## 【API 与前端边界】

API 在既有 loopback 进程中新增最小业务路由；必须经 Application Service，不能 SQL 直连：

```text
GET    /api/v1/exploration-tracks
POST   /api/v1/exploration-tracks
GET    /api/v1/exploration-tracks/:id/history
PATCH  /api/v1/exploration-tracks/:id
DELETE /api/v1/exploration-tracks/:id
POST   /api/v1/exploration-tracks/:id/restore

POST   /api/v1/items                 （仅可选扩展既有 CaptureIdeaInput）
PUT    /api/v1/items/:id/exploration-track
DELETE /api/v1/items/:id/exploration-track
GET    /api/v1/items/:id/exploration-track
```

API 路由、request / response DTO、大小限制、错误码和 unknown-outcome 策略必须在实施前另建路由矩阵并由产品确认。新增所有写请求沿用既有规则：无幂等键、未知提交不自动重试、仅重新读取真实状态。

前端仅在 API / Application 契约冻结和设计交付后实施；它只消费 `ExplorationTrack*` 读模型与明确关联上下文，不持久化业务镜像，不回落 IndexedDB，不补写关系。

## 【自动化测试与验收门】

1. Migration：004 在日常 / UAT 临时数据库独立执行、幂等、checksum 漂移拒绝；app DML-only，migrator 仅目标库权限。
2. 名称：空白、超 80 code point、NFKC / 大小写同名、并发同名创建、改名冲突、删除后同名创建和恢复冲突。
3. 主线：创建空主线、改名、软删除、恢复；删除 / 恢复期间关联 Item / Review / 状态事件快照零变化。
4. 原子捕获：已有主线、新建并归入、Item 插入失败、初始 Event 失败、commit 前失败均比较 Track / Item / Event 快照；失败不留半成型主线或 Item。
5. 关联：归入、改归入、移除、deleted Track / Item 拒绝、并发调整、每 Item 最大一关联。
6. 读模型：空主线、稳定排序、最近事项、已放弃收纳、回收站隐藏、软删除 Track 降级、真正缺失外键降级、复盘摘要与无摘要。
7. 删除恢复：主线与 Item 的交叉删除 / 恢复，关系不丢失、不重建、不伪造。
8. Backup：v1 / v2 旧备份安全恢复为空关系；V3 十集合导出—清空—恢复—导出规范化等价；非法 Track / Item 引用零写入；末端失败全量回滚；metadata 隔离。
9. API：矩阵路由、404 / 409 / 400 / 503 / 500、脱敏、requestId、无额外管理路由、未知写入结果不自动重试。
10. H5：桌面与小屏加载 / 空态 / 失败 / 草稿保护、旧响应保护、查看事项真实定位；Network / Storage 确认只使用 loopback API 和 MySQL。
