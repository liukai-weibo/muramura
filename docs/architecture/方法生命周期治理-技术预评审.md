# 方法生命周期治理：移入回收站与关联历史保护 — 技术预评审

> 状态：**产品已选择方案 B；P0/P1 验收前仍不允许开发。**
> 范围：产品提出的「方法详情页 → 更多操作 → 移入回收站 → 30 天内恢复 → 到期永久清理后保留最小历史墓碑」能力。
> 本文已完成产品裁决记录；待 P0/P1 关闭后，必须进行第二阶段架构冻结，才可进入实施。

## 【技术结论：有条件可行】

产品提出的 UI 入口与风险控制方向正确：方法删除应为详情页低频的「移入回收站」，不应放入列表 Hover 操作或与「用此方法开始行动」并列的常驻主操作。

但它不是纯 UI 改动，而是**方法对象生命周期扩展**。当前系统仅对 `Item` 提供软删除、恢复及 30 天后永久清理；`Method` 没有 `deletedAt`、方法回收站查询、恢复或清理契约。因此当前不允许交给前端直接开发。

同时，当前工作区已出现 P0/P1 的最小修复实现痕迹：

- `MethodApplicationContextResult` 已提供 `no-association / available / unavailable`；
- 事项永久清理已尝试清理悬空 `MethodVersion.sourceReviewId`；
- 备份导入已尝试对断裂的可选 `sourceReviewId` 做受限归一化。

但这些改动尚未经过本轮要求的自动化测试、端到端导出—恢复验证及 QA 验收，**不能视为 P0/P1 已关闭**。在其关闭前，不应扩大任何删除链路的对象范围。

## 【已确认的产品裁决】

产品已冻结以下业务语义：

```text
方法移入回收站
→ 30 天内可恢复，并保留可识别历史关系
→ 到期永久清理方法本体和可复用内容
→ 保留最小历史墓碑
→ 历史事项、复盘和证据中的关系不消失、不伪装、不猜测
```

### 回收站期内

- 统一展示：`关联方法：{title}（已移入回收站）`；
- 方法从正常列表、全局搜索结果、验证候选、修订候选与行动发起入口移除；
- 不可成为默认或可选验证 / 修订方法；
- 保留方法本体、版本、证据和方法应用关系；
- 在统一入口 `数据与设置 → 回收站 → 全部 / 事项 / 方法` 内可恢复；
- 恢复后重新成为正常可用方法，既有版本与关联原样恢复；
- 方法详情页不提供直达永久清理入口。

### 永久清理后

- 删除方法本体、全部可复用步骤、补充说明与版本正文；
- 创建并保留只读、不可复用、不可恢复正文的最小历史墓碑；
- 历史展示统一为：`关联方法：{历史方法名称}（已永久清理）`；
- 墓碑只承担历史解释，禁止作为验证、修订或发起行动的依据；
- 禁止按名称、时间、版本号或文案推测、重连任何关系。

产品明确拒绝方案 A（永久清理后删除所有可识别关联）。


- `Item.deletedAt` 的软删除、恢复、30 天清理流程可作为生命周期交互与服务边界的参考，不能直接套用到 `Method`；
- `ItemApplicationService.listTrash()`、`restoreItem()` 与 `purgeDeletedBefore()` 可用于抽象出方法侧所需的对称能力；
- `Method`、`MethodVersion`、`MethodEvidence`、`MethodApplication` 已有结构化关系；
- 当前备份包含方法、版本、证据、应用关系的完整集合；
- 已定义的 `MethodApplicationContextResult` 可作为前端诚实降级的基础，但其原因集合尚不足以表达「方法在回收站」。

## 【可复用现有能力】

| 能力 | 当前事实 | 结论 |
|---|---|---|
| 方法软删除 | `Method` 无 `deletedAt` | 不支持 |
| 方法回收站列表 | `MethodRepository` 无 `listDeleted()` | 不支持 |
| 方法恢复 | `MethodRepository` 无 `restore()` | 不支持 |
| 方法 30 天永久清理 | 无方法侧 `purgeDeletedBefore()` | 不支持 |
| 方法版本、证据保留 | 当前均依附于活跃方法存在 | 仅能在方法本体仍存在时保留 |
| 方法应用关联 | `MethodApplication` 强引用 `methodId + methodVersion` | 永久删除方法时必须处理 |
| 复盘事实 | `Review` 不直接引用方法 | 可独立保留 |
| 完整备份恢复 | P0 修复尚未验收 | 不能作为新增删除能力前提 |

## 【数据可信边界】

### 1. 30 天回收站期内

若方法移入回收站，最小可信语义应是：

```text
方法本体、全部版本、证据和方法应用关系仍保留
→ 不出现在正常方法列表、正常搜索与可复用方法选择中
→ 可在回收站恢复
→ 历史查看必须明确表示“方法已移入回收站”
```

此时关联并非缺失，不能返回 `no-association`，也不能误报 `method-missing`。为了让 UI 不猜测，读模型至少要新增一个结构化分支，例如：

```ts
{
  status: 'unavailable',
  application,
  reason: 'method-in-trash',
}
```

或以同等明确的独立状态表达。具体命名由实施前 Contracts 评审冻结。

在此状态下：

- 允许完成纯事实复盘；
- 禁止把该方法作为默认验证对象或可选验证方法；
- 禁止自动修订、自动重连或把它作为“正常可用来源方法”；
- 恢复后才重新回到可用状态。

### 2. 30 天到期永久清理后：已冻结为方案 B（最小历史墓碑）

产品已裁决采用方案 B，拒绝方案 A。

永久清理时删除 `Method` 及全部 `MethodVersion` 的可复用内容，但必须保留一个最小、不可恢复方法正文、不可参与行动或验证的历史身份记录，使历史页面可表达：

```text
关联方法：{历史方法名称}（已永久清理）
```

墓碑不是隐藏方法副本：不保存步骤、适用情况、不适用情况或版本正文；只承担历史证据链解释。

### 冻结前的推荐最小实现模型

新增独立的 `MethodTombstone`，使用原 `methodId` 作为稳定身份：

```ts
interface MethodTombstone {
  methodId: string
  title: string
  purgedAt: string
}
```

理由：

- `MethodApplication`、`MethodEvidence` 已用 `methodId` 关联，墓碑复用该稳定标识即可保留事实关系；
- 不需要把完整方法正文复制到历史对象；
- 不需要根据标题、时间或版本号猜测原关系；
- 导入校验可明确要求：一个 `methodId` 必须对应活跃 / 回收站中的 `Method`，或对应一个 `MethodTombstone`，不能两者都无；
- 永久清理后可删除 `MethodVersion` 正文，同时保留 `MethodApplication.methodVersion` 作为“当时使用的版本号”这一事实字段；不得据此尝试恢复版本内容。

此模型仍需在第二阶段架构冻结时确认字段命名及恢复不变量，但不得退化为页面本地缓存或纯展示文本。

### 建议的结构化读取状态

当前三态结果不足以表达产品已确认的两种生命周期状态。建议演进为等价的显式联合读模型：

```ts
type MethodApplicationContextResult =
  | { status: 'no-association' }
  | { status: 'available'; application: MethodApplication; method: Method; version: MethodVersion }
  | { status: 'method-in-trash'; application: MethodApplication; method: Method; version: MethodVersion }
  | { status: 'method-purged'; application: MethodApplication; tombstone: MethodTombstone }
  | { status: 'unavailable'; application: MethodApplication; reason: 'method-missing' | 'version-missing' | 'method-and-version-missing' }
```

其中：

- `method-in-trash` 是已知、可恢复、但不可复用的真实状态；
- `method-purged` 是已知、不可恢复正文、但历史关系仍可解释的真实状态；
- 既有 `unavailable` 继续仅表达异常断裂，不能拿来承载正常的软删除或墓碑业务状态；
- 前端只能按 `status` 展示，禁止用 `undefined`、catch、标题或版本号分支猜测。

### 方案 B 的代价

- 必须新增数据对象 / 字段及生命周期规则；
- 涉及 Schema、Migration、备份恢复、导入校验、搜索过滤与读模型；
- 不属于当前轻量 UI Sprint；
- 当前 P0/P1 未验收前，不能实现。


## 【最小新增能力】

在 P0/P1 验收关闭且产品选择策略后，方法回收站至少需要：

1. `Method` 增加软删除生命周期信息，例如 `deletedAt?: string`；
2. 新增最小 `MethodTombstone` 持久化对象，用原 `methodId`、最后已知标题和永久清理时间解释历史关联；
3. `MethodRepository` / Application 新增：
   - 移入回收站；
   - 回收站列表；
   - 恢复；
   - 30 天到期永久清理；
3. 正常方法列表、搜索、方法选择器排除已删除方法；
4. 历史读模型结构化表达“方法在回收站”，禁止 UI 通过空值推测；
6. 永久清理事务中：创建墓碑、删除方法本体和版本正文、保留证据与方法应用关系，并使导出备份保持可恢复；
7. 备份导出、导入、恢复完整覆盖方法软删除、墓碑与严格引用校验；
8. 前端在稳定 Application 契约后，再实现更多操作、确认层、回收站和诚实降级展示。

## 【是否涉及 Schema / Migration / 备份】

| 边界 | 结论 |
|---|---|
| Domain 状态机 | 不应涉及事项状态机；方法生命周期规则需在 Application / Repository 明确 |
| Contracts | 必须涉及 |
| Application | 必须涉及 |
| Repository | 必须涉及 |
| IndexedDB Schema | 必须涉及：`Method` 软删除需要持久化字段与索引策略 |
| Dexie version / Migration | 必须涉及 |
| JSON 备份数据 | 必须涉及：新增墓碑集合、方法软删除状态及导入校验语义 |
| `BackupDocument.version` | **建议升级为 v2**：导出 v2；导入兼容 v1 并补为空墓碑集合。不得假装 v1 与含墓碑的完整备份语义完全相同。 |
| 前端 | 后置，仅适配已冻结契约 |

说明：即使 `deletedAt` 是可选字段，备份格式的**业务语义**已改变；不能仅因 JSON 仍能解析，就宣称“未涉及备份”。

## 【风险与保护策略】

1. **先关 P0/P1，再扩展删除范围**：当前数据可信性修复必须完成测试、导出—恢复复现和 QA 验收。
2. **不允许页面层删除**：前端不得直接操作 Dexie，不得在 UI 本地删关系以“看起来正常”。
3. **不允许模糊空值**：方法在回收站、方法已永久清理、从未关联方法是不同事实，必须有结构化读模型。
4. **永久清理全事务执行**：创建墓碑、删除方法与版本正文、保留历史关联的处理必须在同一 IndexedDB 事务中完成。
5. **恢复必须是原子操作**：恢复成功后方法、版本、证据、应用关系回到一致状态；不接受部分恢复后静默成功。
6. **禁止同名冲突伪问题化**：当前 `Method.id` 是稳定身份，同名并不破坏数据一致性；除非产品新增名称唯一性规则，否则恢复不应因同名而失败。
7. **搜索隔离**：正常全局搜索不能命中回收站方法；是否在回收站内提供局部搜索由产品 / 设计单独定义。
8. **不做自动重连**：任何断裂关系不得按标题、时间、步骤或版本号猜测重连。

## 【测试建议】

### P0/P1 前置验收

- 三态方法应用上下文：`no-association / available / unavailable`；
- 方法缺失、版本缺失、双缺失的结构化降级；
- 永久清理事项后，存活方法版本不保留断裂 `sourceReviewId`；
- 系统导出备份可由同系统恢复；
- 旧备份仅 `sourceReviewId` 断裂时可受限归一化恢复；
- 必填关系断裂仍必须拒绝恢复。

### 方法回收站实施后的自动化回归

- 移入回收站后从正常列表、搜索、方法选择器排除；
- 回收站可列出方法并在 30 天内完整恢复；
- 关联事项读取到 `method-in-trash` 与 `method-purged` 两种结构化状态；
- 两种状态均不触发自动验证、修订、替代方法或行动发起；
- 30 天到期清理会创建最小墓碑、删除方法与版本正文、保留可解释的证据和应用关系；
- 清理前、清理后导出备份均可恢复；
- 恢复后的版本、证据与方法应用关系一致；
- 事务失败时不产生部分删除或部分恢复。

### H5 人工 UAT

- 详情页低频入口、影响说明、二次确认和取消；
- 删除后当前详情、列表选中、Toast 与回收站入口的稳定状态；
- 回收站恢复后返回正常列表与详情定位；
- 关联事项 / 复盘中“在回收站”“永久清理后”的诚实降级；
- 与全局搜索、流转历史抽屉、删除 / 恢复确认层的层级和互斥；
- 数据导出—清空—恢复后的可读性与关系一致性。

## 【交付给研发的技术约束】

- 产品已选择方案 B；后续架构冻结应确认 `MethodTombstone` 的最终契约、备份 v2 与 v1 导入兼容规则；
- P0/P1 未通过后端自动化测试、导出—恢复验证及 QA 验收前，不建立方法删除入口；
- 不得将 `Method` 删除实现为仅删除 UI 列表项；
- 不得把方法在回收站或永久删除后的关系，降级为前端 `undefined` / catch / 文案猜测；
- 不得放宽所有备份引用校验以换取恢复成功；
- 不得删除复盘事实以规避方法引用完整性问题；
- 产品未在方案 A / B 中作出永久清理历史关系裁决前，不得实现方法永久清理。

## 【已关闭的产品裁决】

产品已确认：

1. 回收站期内展示“方法已移入回收站”，并从一切可复用候选中排除；
2. 30 天到期永久清理采用方案 B：最小历史墓碑；
3. 不接受永久清理后丢失可识别历史关联的方案 A；
4. 使用 `数据与设置 → 回收站` 统一入口，并按 `全部 / 事项 / 方法` 筛选。

## 【仍需架构冻结的问题】

1. 墓碑最终契约、唯一性与写入事务顺序；
2. `method-in-trash` / `method-purged` 的 Contracts 具体形状与所有读模型覆盖范围；
3. 备份 v2 导出、v1 导入兼容、墓碑引用严格校验；
4. 在删除来源事项 / 复盘时，指向墓碑方法的 `MethodEvidence` 如何保留或删除的精确规则；
5. 统一回收站的跨对象分页 / 排序读模型是否维持简单的前端合并，或应新增 Application 读模型。后者由产品的列表规模要求决定，当前不得预建复杂查询。
