# 探索主线 V1 S3 切片 5：受控故障注入架构授权

> 日期：2026-07-26
> 责任岗：架构师
> 状态：**仅授权 QA 在隔离 UAT 完成下述两项验证；不构成封板或新增编码授权。**

## 1. 结论与不变量

切片 5 可采用以下两种受控、可回滚的运行时故障注入。它们只作用于 `knowledge_base_uat`，不修改项目源码、测试源码、配置文件、MySQL 容器、运行库结构、migration 或 `mysql-data`。

每一场景必须在显式加载 `.env.uat`、`GET http://127.0.0.1:32146/health` 已确认 `database=knowledge_base_uat`、`schemaVersion=4` 后开始。日常 `knowledge_base` 仅取前后只读深度快照，必须为 `SNAPSHOTS_IDENTICAL`。

禁止以请求前停止 API 证明响应丢失；禁止以停止 API 伪造 MySQL 503；禁止浏览器直连 MySQL、IndexedDB fallback、自动重试、补偿写入或通过直接查询数据库确认业务结果。

## 2. 场景 A：真实写入完成后的响应投递丢弃

### 授权的注入方式

QA 仅在本次 Playwright / 浏览器 UAT 运行时，以 `page.addInitScript` 或等价 DevTools Runtime 一次性包装页面的 `window.fetch`：

1. 对目标写请求先调用原始 `fetch`；
2. 仅在原始 promise 已成功返回 Response 后，针对这一条预先指定的探索主线写请求向应用层抛出 `TypeError`；
3. 不把该 Response 返回给页面应用；后续读取请求不拦截、不篡改。

这不是源码或配置变更，也不伪造服务器写入：API 已实际收到并完成该请求，只有响应到页面应用的投递被测试运行时丢弃。对前端而言，该状态与真实响应丢失不可区分，适用于验证 unknown-outcome 合约。

### 执行步骤与通过条件

1. 记录 UAT / 日常库前快照、`/health` 和浏览器初始页面。
2. 准备一个唯一、可辨识的单次提交；仅允许发送一次目标 POST / PUT / DELETE。禁止点击重试或第二次提交。
3. 注入一次响应投递丢弃并完成该提交。浏览器证据必须显示仅一条目标写请求；应用不得显示成功状态。
4. 验证前端进入 unknown-outcome：草稿、改名输入、确认层及明确关联选择仍保留；写控件保持受控；没有自动重发。
5. 解除一次性运行时注入后，只通过冻结 GET API 重新读取确认事实。若写入已提交，显示真实新状态；若未提交，显示真实未变状态。两种结果都不允许由本地草稿推断。
6. 记录重读前后的浏览器 Network、页面状态、API 结果及两个运行库后快照。

若运行时注入未导致页面进入 unknown-outcome，或发现第二个写请求，该次场景失败；不得改源码绕过，应恢复合法空 Backup V3 UAT 基线后重新人工执行一次。

## 3. 场景 B：API 对 MySQL 的真实不可用映射

### 授权的注入方式

先正常停止当前 UAT API 进程，再启动**专用故障 API 进程**：显式加载 `.env.uat`，仅在该进程环境中覆盖 `MYSQL_APP_PASSWORD` 为无效值。不得写入或编辑 `.env.uat`，不得改变 MySQL 用户、权限、容器、端口或网络规则。

此故障进程仍固定监听 `127.0.0.1:32146` 并指向 `knowledge_base_uat`；其 MySQL 认证会产生 `ER_ACCESS_DENIED_ERROR`，该错误是既有 `isMySqlUnavailable()` 的明确输入，故 API 应返回 `503 MYSQL_UNAVAILABLE`。这验证的是 API 到 MySQL 的真实依赖不可用，不是 API 停止或浏览器网络失败。

### 平台执行命令（Windows，前台专用子进程）

不得使用 `pnpm uat:api` 或 `scripts/start-uat-api.sh`，因为它们包含 migration。正常 UAT API 已停止后，平台或 QA 应在 `Knowledge_Base` 目录启动一个独立、前台的 PowerShell 子进程，执行下列命令；窗口保持运行即表示故障 API 保持运行，关闭窗口即停止它。

```powershell
& powershell.exe -NoProfile -Command @'
$envFile = Join-Path (Get-Location) '.env.uat'
Get-Content -Encoding UTF8 $envFile | ForEach-Object {
  $line = $_.Trim()
  if ($line -and -not $line.StartsWith('#')) {
    $pair = $line -split '=', 2
    if ($pair.Count -eq 2) { Set-Item -Path ("Env:" + $pair[0].Trim()) -Value $pair[1].Trim() }
  }
}
$env:MYSQL_APP_PASSWORD = '__qa_invalid_uat_password__'
& 'C:\Users\Administrator\AppData\Local\hermes\node\corepack.cmd' pnpm --filter @knowledge-base/api start
'@
```

该命令只读取 `.env.uat`，随后在专用子进程环境中覆盖密码；它不写入任何文件、不执行 migration，也不启动容器。平台如不能执行嵌套 PowerShell，应以等价方式创建同一前台进程：加载 `.env.uat` 的变量、仅覆盖其 `MYSQL_APP_PASSWORD`、直接运行 `corepack pnpm --filter @knowledge-base/api start`，并且不得调用任何 migrate、restore 或 Docker 命令。

### 执行步骤与通过条件

1. 在正常 UAT API 下记录 `/health` ready、两个库前快照与页面中已有真实数据。
2. 停止正常 UAT API；仅启动上述进程环境覆盖的故障 API。不得执行写请求、迁移、恢复或容器操作。
3. 访问既有 `/health`，预期 HTTP 503；以 H5 触发一个冻结 GET 读取，预期既有错误 DTO 为 `code=MYSQL_UNAVAILABLE` 且包含 `requestId`。不得新增或依赖 `diagnosticId`、health 字段、路由或 DTO。
4. 验证前端不将失败降级为空数据、不清空草稿或明确选择、不发起自动重试，也不产生补偿写入。
5. 停止故障 API，以未修改的 `.env.uat` 启动正常 UAT API；`/health` 必须恢复为 ready、`database=knowledge_base_uat`、`schemaVersion=4`。
6. 仅由用户触发重新读取 API 确认真实数据；记录浏览器 Network、API 响应、前后快照和恢复条件。

任何错误的 database/schemaVersion、非 503 映射、泄露认证/SQL 信息、空数据伪装、自动写入或日常库快照变化均为阻断缺陷。停止故障 API 并恢复正常 UAT API 后，转架构师复审。

## 4. 证据与完成条件

QA 报告每场景必须包含：目标库和 health 原文、前后深度快照、单次写请求或读取请求的 Network 证据、页面草稿/选择状态、API 错误 DTO（含 requestId）、恢复后的显式重读结果，以及未触及日常库的证据。

两场景均完成且其余切片 5 浏览器 UAT 通过后，QA 才可回流架构复审。此授权不改变“未经新的 QA 通过、架构复审和产品最终验收，探索主线 V1 不得封板”的结论。
