# 数据可信性与备份恢复修复：技术评审

> 状态：待产品确认架构策略后进入实现
>
> 类型：P0 数据可信性与备份恢复修复
>
> 本文不包含代码实现

## 一、技术结论：有条件可行

问题可以在当前本地优先架构中以有限、可测试的改动修复，但不能只通过前端兜底文案解决。

本次必须冻结两项策略：

```text
MethodApplication 读取
→ 区分未关联与关联断裂
→ 前端基于结构化状态诚实降级

永久清理
→ 维护仍存活数据的引用完整性
→ 保证系统导出的 JSON 总能被同一系统恢复
```

推荐采用：

1. 将 `getContextForItem()` 改为结构化联合读模型，明确返回 `no-association`、`available` 或 `unavailable`；
2. 永久清理来源事项 / 复盘时，删除对应证据，并对仍存活方法版本的 `sourceReviewId` **清空为未记录来源**；
3. 保持恢复校验严格：导出的 JSON 中不允许存在指向已删除复盘的 `sourceReviewId`；
4. 不新增墓碑、不新增 Schema、不修改 JSON 备份格式；
5. 对已存在的历史断裂备份，采用一次性的导入兼容归一化：仅清空可确认失效的可选 `sourceReviewId`，不伪造复盘、不重连到其他记录。

这是一条低维护成本、数据可恢复、可追溯且不会伪造历史事实的路径。

## 二、现状复现与根因

### 2.1 方法应用上下文读取的语义坍缩

当前 `IndexedDbMethodApplicationRepository.getContextByItemId(itemId)` 的逻辑为：

```text
查询 MethodApplication
→ 查询 Method
→ 查询冻结 MethodVersion
→ 三者都存在才返回 MethodApplicationContext
→ 任一缺失则返回 undefined
```

因此 `undefined` 同时可能表示：

```text
A. 事项从未关联方法
B. 存在 MethodApplication，但方法不存在
C. 存在 MethodApplication，但冻结版本不存在
D. 方法和冻结版本都不存在
```

这把“确无关联”和“历史关联不可用”压缩为同一个返回值。前端无法从 `undefined` 诚实判断原因，也不得依赖异常、文案、时间或版本号猜测。

### 2.2 永久清理造成自导出备份不可恢复

当前永久清理事项时，若该事项存在复盘，清理逻辑会：

```text
删除该复盘关联的 MethodEvidence
删除该复盘派生的 ItemLink
删除该事项 MethodApplication / ItemLink / 状态事件
删除事项与复盘
```

但对于仍然存活的方法，当前逻辑没有同步处理：

```text
MethodVersion.sourceReviewId
```

若该版本仍指向被永久清理的复盘，就形成：

```text
MethodVersion.sourceReviewId → 不存在的 Review
```

完整 JSON 导出会保留该悬空 ID，而导入校验要求：

```text
sourceReviewId 必须引用存在的 Review
```

于是会出现：

```text
系统成功导出自身当前数据
→ 系统拒绝恢复该导出文件
```

这是 P0：违反“完整备份必须可恢复”。

## 三、断裂关联的结构化读模型契约

### 3.1 推荐契约

将现有可选返回：

```ts
getContextForItem(itemId): Promise<MethodApplicationContext | undefined>
```

替换为显式联合类型：

```ts
type MethodApplicationContextResult =
  | {
      status: 'no-association'
    }
  | {
      status: 'available'
      application: MethodApplication
      method: Method
      version: MethodVersion
    }
  | {
      status: 'unavailable'
      application: MethodApplication
      reason: MethodApplicationUnavailableReason
    }

type MethodApplicationUnavailableReason =
  | 'method-missing'
  | 'version-missing'
  | 'method-and-version-missing'
```

`unavailable` 必须保留完整的 `application`，从而向前端提供唯一可信的降级事实：

```text
有关联记录
+ 关联的 methodId
+ 关联的冻结 methodVersion
+ 当前不可读取原因
```

### 3.2 判定规则

| `MethodApplication` | `Method` | 冻结 `MethodVersion` | 返回 |
|---:|---:|---:|---|
| 不存在 | — | — | `no-association` |
| 存在 | 存在 | 存在 | `available` |
| 存在 | 不存在 | 存在 / 不存在 | `unavailable: method-missing` 或 `method-and-version-missing` |
| 存在 | 存在 | 不存在 | `unavailable: version-missing` |

为保证原因准确，Repository 必须独立读取方法与版本，不能因为方法缺失就短路而忽略版本是否存在。

### 3.3 前端可信文案

前端必须依据 `status` 与 `reason` 展示，禁止自行推断。

| 结构化结果 | 建议文案 | 是否允许默认验证 / 修订 |
|---|---|---:|
| `no-association` | `本次事项未关联方法。` | 否 |
| `available` | `本次行动使用了「{method.title}」v{application.methodVersion}。` | 可按产品规则默认验证 |
| `method-missing` | `本次事项保留了方法关联，但关联方法已不可用。` | 否 |
| `version-missing` | `本次事项保留了方法关联，但实际使用的历史版本已不可用。` | 否 |
| `method-and-version-missing` | `本次事项保留了方法关联，但关联方法和历史版本均已不可用。` | 否 |

`unavailable` 的复盘约束：

```text
允许正常完成事实复盘
+ 不自动选择方法处理
+ 不自动验证
+ 不自动修订
+ 不自动重连到其他方法
+ 不伪造方法名称、步骤或版本内容
```

用户如主动选择“验证已有方法”，仍是新的明确操作，不应被视为修复旧关联。

## 四、永久清理的引用完整性策略

### 4.1 受影响关系清单

永久清理一个软删除到期的事项，涉及：

```text
Item
├── Review（该事项唯一复盘）
│   ├── MethodEvidence.reviewId
│   ├── MethodVersion.sourceReviewId
│   └── ItemLink.sourceReviewId
├── MethodApplication.itemId
├── ItemLink.targetItemId
└── ItemStatusEvent.itemId
```

还需要考虑方法的独立价值：

```text
Method
├── MethodEvidence.methodId
├── MethodVersion.methodId
└── MethodApplication.methodId
```

当前业务原则是：若方法没有剩余证据且没有剩余方法应用，永久清理可一并删除该方法及其版本；若方法仍有证据或应用，则它仍具有独立业务价值，必须保留。

### 4.2 推荐策略：清理无效可选来源引用

当来源事项及其复盘永久清理时：

1. 删除该复盘相关的所有 `MethodEvidence`；
2. 找出 `sourceReviewId === deletedReview.id` 的所有 `MethodVersion`；
3. 对**仍存活的方法版本**，将该可选字段更新为：

```ts
sourceReviewId: undefined
```

4. 然后依据现有规则：

```text
方法剩余证据数 = 0
且 方法应用数 = 0
→ 删除 Method 与其全部 MethodVersion

否则
→ 保留 Method 与剩余 MethodVersion
```

5. 删除来源 `ItemLink`、事项方法应用、目标 `ItemLink`、状态事件、复盘和事项。

### 4.3 策略语义

清空 `sourceReviewId` 不表示：

```text
该版本从未有来源复盘
```

它表示：

```text
该版本的来源复盘已被永久清理，当前系统不再保留可读取来源。
```

但现有数据结构没有字段记录“为何为空”。因此 UI 不得把空 `sourceReviewId` 明确展示为“来源已清理”。只能诚实表示：

```text
暂无可用来源复盘。
```

这不是伪造事实；系统确实不再拥有该来源复盘。

### 4.4 为什么不推荐本轮采用墓碑

墓碑方案可以更精细地区分：

```text
从未记录来源
vs
来源已永久清理
```

但至少需要：

- 新实体或新字段；
- IndexedDB Schema 修改；
- Migration；
- JSON 备份格式修改；
- 导入校验规则调整；
- 墓碑生命周期与隐私语义；
- 新的读取模型和测试矩阵。

本问题的不可退让目标是“导出即能恢复”，而不是永久保留已清理复盘的存在证明。采用墓碑会把 P0 修复扩大为新的历史归档能力，维护成本不成比例。

### 4.5 为什么不推荐放宽导入校验以接受任意断裂引用

若导入校验直接允许任何不存在的 `sourceReviewId`：

- 外部损坏备份会被悄然接受；
- 引用完整性边界失效；
- 无法区分合法清理结果与异常数据损坏；
- 后续读模型和清理逻辑需要永久容忍悬空引用。

因此不建议将“任意断裂引用可恢复”作为默认恢复策略。

推荐保持：

```text
系统当前导出的备份
→ 严格完整
→ 可以恢复

旧历史备份中由已知旧版本 Bug 产生的可选 sourceReviewId 断裂
→ 在导入前做有限、可审计的兼容归一化

其他必填关系断裂
→ 拒绝恢复
```

## 五、导入 / 导出兼容策略

### 5.1 新修复后的正常路径

永久清理事务完成后不保留悬空 `sourceReviewId`，因此：

```text
exportData()
→ 产生引用完整 JSON
→ parseAndValidate()
→ 正常通过
→ replaceData()
→ 正常恢复
```

备份格式不变。

### 5.2 旧备份兼容归一化

为保护已由旧版本导出的历史备份，导入前可以在 `parseAndValidate()` 中执行有限归一化：

```text
发现 MethodVersion.sourceReviewId 不存在于 reviews
→ 将该版本 sourceReviewId 清空
→ 记录兼容修复数量
→ 继续执行其他完整性校验
```

限制：

- 仅处理 `sourceReviewId`，因为它在类型上已经是可选来源引用；
- 不处理 `MethodEvidence.reviewId`，它是证据的必填关系，断裂仍必须拒绝；
- 不处理 `MethodApplication.methodId / methodVersion / itemId`，断裂仍必须拒绝；
- 不伪造 `Review`、`Item`、`Method` 或 `MethodVersion`；
- 不把断裂重新关联到任何“可能相近”的记录。

### 5.3 用户可解释性

兼容导入成功后，应由 Application 返回或 UI 展示：

```text
已恢复备份。
其中 N 条历史方法版本的来源复盘已不可用，已按兼容规则保留版本内容并移除无效来源引用。
```

是否要让 `parseAndValidate()` 返回规范化报告，可作为最小 Application 返回值扩展；如果暂不扩展 UI，至少必须在自动化测试中明确归一化发生。

### 5.4 备份版本结论

不需要提升 `BackupDocument.version`，因为：

- 数据集合不变；
- `sourceReviewId` 本来就是可选字段；
- 新旧文档都可由同一格式解析；
- 行为变化属于恢复兼容策略，不是文件结构变化。

## 六、是否涉及 Schema / Migration / 备份

| 层级 | 是否修改 | 说明 |
|---|---:|---|
| Domain | 否 | 状态机和核心业务语义不变 |
| Contracts | 是，最小 | `MethodApplicationContext` 改为结构化联合读模型；可增加恢复归一化报告 |
| Application | 是，最小 | 暴露结构化方法应用上下文；组织兼容恢复反馈 |
| Repository | 是，最小 | 读取关联断裂原因；永久清理时清空无效 `sourceReviewId` |
| IndexedDB Schema | 否 | 只更新现有记录字段，字段已存在且可选 |
| Migration | 否 | 新清理逻辑向前生效；旧备份在导入时归一化 |
| JSON 备份格式 | 否 | 数据结构、版本和集合保持不变 |
| 导入校验逻辑 | 是，最小 | 先归一化可选 `sourceReviewId` 断裂，再执行严格校验 |
| Docker / 部署 | 否 | 不涉及 |

## 八、历史数据保护与降级策略

### 8.1 已存本地数据库

新逻辑不会自动扫描和修改所有当前数据库记录。

原因：无法确定某个既有悬空 `sourceReviewId` 是否由旧清理 Bug 产生，还是存储被非正常篡改。自动全库修复会掩盖异常来源。

保护策略：

```text
新发生的永久清理
→ 在清理事务内维护引用完整性

导入旧备份
→ 只对可选 sourceReviewId 做受限归一化

现有运行时异常关系
→ 结构化 unavailable 降级，不伪造可用上下文
```

如果产品要求对现有本地库做主动修复，应单独立项，先定义扫描、报告、备份和用户确认流程。

### 8.2 关联断裂的运行时展示

`unavailable` 不是“无关联”的同义词。

UI 必须：

- 展示历史关联不可用；
- 保留 `methodId` 与 `methodVersion` 作为内部结构化事实，但不在没有名称时伪造名称；
- 允许用户完成事实复盘；
- 禁止自动默认验证；
- 禁止自动修订；
- 禁止自动关联到当前版本或其他方法。

### 8.3 方法版本来源缺失

当 `MethodVersion.sourceReviewId` 被清空或旧数据本来为空：

- 版本本身继续可读；
- 版本的步骤、说明、版本号和创建时间继续可读；
- 来源复盘入口不显示或显示“暂无可用来源复盘”；
- 不搜索、创建或伪造来源复盘。

## 九、风险与保护策略

| 风险 | 保护策略 |
|---|---|
| 前端将 `undefined` 当作无关联 | 使用 `status` 联合读模型，UI 仅按 status 展示 |
| 方法缺失时短路导致错误原因 | 独立读取方法和版本，返回精确 unavailable reason |
| 清理时错误删除仍有价值的方法 | 保留现有“无证据且无应用才删方法”判定；仅清空可选来源引用 |
| 自导出备份无法恢复 | 清理事务内先处理 sourceReviewId；加入导出—导入回归测试 |
| 为兼容旧备份接受任意损坏关系 | 只归一化可选 sourceReviewId；其他必填关系继续严格拒绝 |
| 兼容归一化伪造历史 | 只清空无效引用，不创建或重连实体 |
| 恢复期间写入与归一化不原子 | 归一化在校验阶段内完成，replaceData 继续单事务替换 |
| 运行时已有断裂关联被掩盖 | 返回 unavailable；不自动修复、不自动选择方法 |
| P0 修复扩张为墓碑或历史归档系统 | 明确不新增表、字段、Schema、Migration 或备份版本 |

## 十、自动化复现与回归测试方案

### 10.1 方法应用上下文读模型

新增测试：

1. 没有 `MethodApplication`：返回 `no-association`；
2. 应用、方法、冻结版本完整：返回 `available` 与完整结构化对象；
3. 应用存在、方法缺失、版本存在：返回 `unavailable: method-missing`；
4. 应用存在、方法存在、冻结版本缺失：返回 `unavailable: version-missing`；
5. 应用存在、方法和版本均缺失：返回 `unavailable: method-and-version-missing`；
6. 所有 unavailable 情况均不抛出“未关联”式错误；
7. 读取操作不修改任何表。

### 10.2 永久清理引用完整性

建立可复现场景：

```text
形成方法 v1
→ 以该方法发起另一事项，使方法具有独立应用价值
→ 来源事项完成复盘并形成方法后进入回收站
→ 模拟到期永久清理来源事项
```

断言：

1. 来源事项和复盘被清理；
2. 对应 `MethodEvidence` 被清理；
3. 因方法仍有应用，`Method` 仍存在；
4. 因方法仍有应用，`MethodVersion` 仍存在；
5. 留存版本的 `sourceReviewId` 已清空；
6. 方法应用仍指向原方法和冻结版本；
7. 方法应用上下文仍为 `available`，只读来源版本不受影响。

同时覆盖：

- 方法无其他证据和应用时，方法及版本被删除；
- 多个版本中仅部分来源复盘被删除时，只清理对应版本来源；
- 删除由复盘派生的新想法时，不影响无关方法；
- 清理失败时事务回滚，不能出现半清理状态。

### 10.3 导出与恢复

针对上述“方法保留、来源复盘被清理”数据：

```text
永久清理完成
→ createBackup()
→ parseAndValidate(JSON.stringify(backup))
→ restoreBackup()
→ 重新读取
```

断言：

- 校验不拒绝系统自身导出；
- 方法、版本、应用仍可恢复；
- 被清理来源不会被伪造恢复；
- `sourceReviewId` 保持为空；
- 读模型与恢复前一致。

### 10.4 旧备份兼容

构造旧格式但含断裂可选 `sourceReviewId` 的备份：

- 导入后对应 `sourceReviewId` 被清空；
- 其他数据保持不变；
- 备份可恢复；
- 必填的 `MethodEvidence.reviewId` 断裂仍拒绝；
- `MethodApplication` 断裂仍拒绝；
- 不得生成任何缺失实体。

### 10.5 工程回归

实施完成后至少运行：

```text
corepack pnpm typecheck
corepack pnpm test
corepack pnpm build:h5
```

## 十一、交付给实施方的技术约束

1. 本次先实施 Contracts / Application / Repository / IndexedDB 的数据可信性修复，不允许前端先用 `undefined` 或异常文案兜底。
2. `getContextForItem()` 必须用结构化联合结果区分 `no-association` 与 `unavailable`；前端不得猜测缺失原因。
3. `unavailable` 仅允许事实复盘，不得自动验证、修订、重连或展示替代方法。
4. 永久清理必须在同一 IndexedDB 事务内删除复盘相关证据，并清空仍存活版本的失效 `sourceReviewId`。
5. 若方法没有剩余证据和方法应用，继续按现有语义删除方法及版本；不得因修复而保留孤立方法。
6. 当前系统新导出的备份必须保持严格引用完整性，并可由同一系统恢复。
7. 旧备份兼容只允许清空断裂的可选 `MethodVersion.sourceReviewId`；任何必填关系断裂必须继续拒绝恢复。
8. 不新增表、字段、索引、Dexie version、Migration、墓碑、JSON 备份版本或新业务对象。
9. 不修改事项状态机、方法形成 / 验证 / 修订的写入规则、方法应用冻结规则或备份安全恢复流程。
10. 实现完成后必须提交复现测试、导出—恢复回归测试、类型检查、完整测试与 H5 构建结果。

## 十二、实施前产品确认项

技术侧建议产品确认：

1. 永久清理后，方法版本只显示“暂无可用来源复盘”，不承诺区分“从未记录”与“来源已清理”；
2. 已清理来源不会自动保留墓碑、名称、复盘正文或额外历史对象；
3. 历史断裂方法应用的页面必须展示“历史关联不可用”，但允许正常完成事实复盘；
4. 用户主动选择另一个已有方法进行验证，属于新的明确方法决策，不会修复或改写旧关联。
