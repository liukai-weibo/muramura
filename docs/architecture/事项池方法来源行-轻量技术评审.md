# 事项池方法来源行 — 轻量技术评审

> 状态：**架构已确认需新增批量展示读模型；当前不允许前端自行拼接或逐项查询。**
>
> 前置能力：`MethodApplicationContextResult`、方法回收站与 `MethodTombstone` 已稳定。

## 【技术结论：有条件可行】

产品方案可行：普通事项详情移除“大方法卡片”，事项池条目以低权重来源行展示方法关联，符合“详情服务当前行动、列表服务快速扫描”的信息层级。

但当前系统**不具备可直接供事项池使用的批量可信读取能力**。现有能力只有：

```ts
methodApplication.getContextResultForItem(itemId)
```

它仅面向当前选中事项；Repository 内部以单个 `itemId` 查询一条 `MethodApplication`，再读取方法、版本和墓碑。若前端对事项池每个条目重复调用该命令，会形成 N+1 异步读取、列表局部到达顺序不稳定及渲染状态复杂度，且不应由页面自行承担关系拼接。

因此必须先新增一个最小的、只读的批量展示 Contract；完成 Application / Repository 实现与测试后，前端才能接入来源行。

## 【可复用现有能力】

以下结构化业务事实可直接复用，**不得由前端重新推导**：

```text
MethodApplication
→ itemId、methodId、冻结 methodVersion

Method
→ 当前可用名称、回收站 deletedAt

MethodVersion
→ 历史冻结版本名称

MethodTombstone
→ 永久清理后的最小历史名称、版本映射

MethodApplicationContextResult
→ no-association / available / method-in-trash / method-purged / unavailable
```

现有单事项语义保持不变：它继续服务详情页复盘流程和方法处理决策。本轮新增的不是另一套关联关系，而是将同一事实映射为列表展示读模型。

## 【最小新增能力】

### 1. 新增只读展示 Contract

在 `packages/contracts/src/index.ts` 新增面向事项池的展示类型：

```ts
export type ItemMethodSourceDisplay =
  | { status: 'no-association'; itemId: string }
  | { status: 'available'; itemId: string; title: string }
  | { status: 'method-in-trash'; itemId: string; title: string }
  | { status: 'method-purged'; itemId: string; title: string }
  | { status: 'unavailable'; itemId: string; title?: string }
```

字段约束：

```text
itemId
→ 必须来自调用方传入的 Item.id；用于前端按 ID 合并，不依赖数组位置。

title
→ 仅在结构化实体中确有名称时提供；不截断、不拼 UI 文案。

unavailable.title
→ 可选。缺失时代表关系已知存在但无任何可读取的可信历史名称。
```

为避免前端按字符串判断，新增 Repository / Application 命令：

```ts
export interface MethodApplicationRepository {
  // existing members
  listSourceDisplaysForItems(itemIds: string[]): Promise<ItemMethodSourceDisplay[]>
}

export class MethodApplicationService {
  listSourceDisplaysForItems(itemIds: string[]): Promise<ItemMethodSourceDisplay[]>
}
```

命名中明确 `Display`，防止后续把该轻量读模型误用于复盘决策、方法验证、版本详情或关系写入。

### 2. 批量读取算法

Repository 在一个只读 Dexie transaction 中：

```text
输入 itemIds
→ 去重并过滤空 ID
→ 一次读取或按唯一 ID 批量读取 MethodApplication
→ 收集关联的 methodId 与 (methodId, frozenVersion) 键
→ 批量读取 Method、MethodVersion、MethodTombstone
→ 对每个输入 itemId 按既有结构化关系映射 ItemMethodSourceDisplay
→ 返回与去重后的输入 ID 一一对应的结果
```

实现可使用 Dexie 的 `bulkGet()` 或等价批量查询；不要求增加索引、Schema 或 Migration。不得在前端循环调用单项 `getContextResultForItem()`，也不得在 Repository 中通过标题、创建时间或版本号猜测缺失关联。

### 3. 标题的可信来源与展示映射

| 结构化结果 | `title` 的唯一可信来源 | 前端展示 |
|---|---|---|
| `no-association` | 无 | 不渲染来源行 |
| `available` | `Method.title` | `方法：{title}` |
| `method-in-trash` | `Method.title` | `方法：{title}（已移入回收站）` |
| `method-purged` | `MethodTombstone.title` | `方法：{title}（已永久清理）` |
| `unavailable` + 方法仍在 | `Method.title` | `方法：{title}（已不可用）` |
| `unavailable` + 版本仍在 | `MethodVersion.title` | `方法：{title}（已不可用）` |
| `unavailable` + 无可读标题 | 无 | `关联方法已不可用` |

说明：`unavailable` 的标题不是猜测。仅当 `Method` 或冻结 `MethodVersion` 仍真实存在时，才读取其持久化标题。两者均不存在且无墓碑时，必须没有 `title` 并展示明确降级文案。

`unavailable` 不应向事项池额外泄露或要求展示 `reason`；其细分原因仍由详情页既有 `MethodApplicationContextResult` 用于更完整的事实复盘降级。

### 4. 前端截断职责

前端只对 `display.title` 做视觉截断：

```text
最多 10 个可见字符
→ 超出追加 …
→ 单行、不换行、不横向滚动
```

截断函数不得修改 `ItemMethodSourceDisplay.title`、Item、Method、MethodVersion、墓碑或缓存中的原始字符串。

“字符”应按 Unicode code point（`Array.from(title)`）计数，避免把 emoji 或代理对截断为无效字符；本轮不需要新增 grapheme-cluster 库。若未来出现组合字形截断摩擦，再单独评审。

## 【数据可信边界】

1. 一个事项是否关联方法，仅由 `MethodApplication.itemId` 的结构化记录决定；
2. 实际使用的方法版本，仅由 `MethodApplication.methodId + methodVersion` 决定；本轮来源行不展示版本号，但不得丢弃或改写冻结版本关系；
3. 正常、回收站、永久清理与断裂状态仅由 Method、MethodVersion、MethodTombstone 的实际存在状态决定；
4. 严禁使用事项标题、方法标题相似性、日期、`updatedAt`、当前版本号、Review 文案或证据计数推断关联；
5. `no-association` 与 `unavailable` 必须保持区分：前者不显示，后者必须诚实提示“已不可用”；
6. 该读模型不提供跳转、筛选、编辑、验证、修订、创建事项或重连能力。

## 【是否涉及 Schema / Migration / 备份】

| 范围 | 结论 |
|---|---|
| Domain 实体与状态机 | 不修改 |
| Contracts | 新增只读展示类型与批量读取方法 |
| Application | 新增只读批量转发方法 |
| Repository | 新增批量结构化查询与映射 |
| IndexedDB Schema / Dexie version / Migration | 不涉及 |
| JSON 备份 / 备份版本 | 不涉及 |
| MethodApplication / Method / Version / Tombstone 写入语义 | 不修改 |

## 【风险与保护策略】

| 风险 | 保护策略 |
|---|---|
| 前端 N+1 查询、加载闪烁 | 只消费一次批量 `listSourceDisplaysForItems()`；按 `itemId` 合并 |
| 异步旧响应覆盖新列表 | 页面为每次列表刷新建立请求序号或 `active` 标记；只有当前请求可提交状态 |
| 回收站与有效事项混淆 | 传入当前可见列表的全部 Item.id；展示读模型不按 Item.deletedAt 擅自过滤 |
| 标题截断污染真实数据 | 截断只发生在渲染值 |
| 断裂关联被隐藏 | `unavailable` 返回明确状态，不降级成 `no-association` |
| 范围膨胀 | 不新增点击、跳转、筛选、详情管理或写入能力 |

## 【测试建议】

### Application / Repository 自动化

至少覆盖：

1. 输入多个无关联事项：均返回各自 `no-association`；
2. 正常关联：返回 `available + Method.title`；
3. 方法在回收站：返回 `method-in-trash + Method.title`；
4. 方法永久清理且有墓碑：返回 `method-purged + MethodTombstone.title`；
5. `method-missing` 但冻结版本仍在：返回 `unavailable + MethodVersion.title`；
6. `version-missing` 但方法仍在：返回 `unavailable + Method.title`；
7. 方法和版本均缺失且无墓碑：返回 `unavailable`，无 `title`；
8. 输入重复 ID、空数组、不存在 Item ID 的稳定行为必须冻结：建议去重后仍返回相应 `no-association`，不抛错；
9. 批量结果不改写任何 MethodApplication、Method、Version、墓碑或 Item；
10. 现有单事项 `getContextResultForItem()`、方法生命周期、备份恢复、断裂关联降级全量回归。

### 前端自动化与人工验收

1. 仅 `available` 显示 `方法：{title}`；无关联没有空行；
2. 回收站、永久清理、断裂三类文案准确；
3. 10 个 code point 内不截断，超出准确追加 `…`；
4. 来源行不可点击、不可聚焦、不产生跳转或筛选；
5. 标题、状态、来源行、时间的视觉优先级符合产品冻结；
6. 普通详情移除大方法卡片，但 `waiting_review` / `reviewed` 的证据、验证、修订上下文不回归；
7. 切换筛选、页码、模块、回收站或异步刷新时，不出现来源串到错误事项的情况。

## 【需要产品经理再次裁决的问题】

无阻断性业务裁决。

实现前仅需产品确认一项非阻断文案细节：对回收站与永久清理状态，是否严格采用已存在的：

```text
（已移入回收站）
（已永久清理）
```

架构建议沿用，以保持方法生命周期既有文案一致性；若产品坚持统一为“（已不可用）”，仍不改变 Contract，只调整前端展示映射。

```text

```
