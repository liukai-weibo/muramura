## 【P1 已关闭：已删除主线关联写入】

复核确认 `assignItemToExplorationTrack()` 与 `removeItemFromExplorationTrack()` 均在同一 MySQL transaction 内先锁定未删除 Item 与关联 Track：

```text
原 Track 缺失
→ code: unavailable
→ 拒绝，零写入

原 Track 已删除
→ code: deleted
→ 拒绝，零写入

目标 Track 缺失
→ code: not-found
→ 拒绝，零写入

目标 Track 已删除
→ code: deleted
→ 拒绝，零写入
```

因此，`track-deleted` 与 `unavailable` 均保留为只读解释状态，不能被关联移除、改派、自动清空、替代或修复。拒绝路径不更新：

```text
items.exploration_track_id
items.updated_at
item_status_events
Review / Method / Version / Evidence / Application / Tombstone / ItemLink
exploration_tracks
```

这符合 S1 Contracts、S2 任务书及已冻结的“软删除保留历史关联”语义。

## 【事务、读模型与错误边界】

已满足：

```text
existing Track：锁 active Track → Item → 初始 Event → 单一事务提交
new Track：唯一规范名竞争保护 → Track → Item → 初始 Event → 单一事务提交
关联调整：Item 前、Track 后的固定锁顺序
所有跨对象失败、约束冲突、Event 失败和 commit 前中断：整体回滚
```

Application 已保持：

```text
名称 NFKC、trim、lower-case、Unicode code point 1..80
活跃与软删除 Track 的全生命周期名称唯一
无 explorationTrack 的 captureIdea() 保持既有行为
existing / new selection 委派给单一 workflow
```

可信读取仍只依赖结构化键：

```text
exploration_tracks.id
items.exploration_track_id
reviews.item_id
```

不由标题、时间、文案、计数、相似度或前端状态推断关系。活跃 / 可选 / 已删除列表、历史、当前事项投影、受限状态定位、`available` / `track-deleted` / `unavailable` / `no-association` 均保持 S2 任务书冻结语义。

## 【架构结论】

S2 满足阶段封板的技术条件，建议产品经理裁决：

```text
探索主线 V1 S2：Repository / Application 与原子工作流，通过并封板
```

S2 封板不得推导为：

```text
探索主线 V1 整体交付
Backup V3 已实现或获准
API 路由 / DTO 映射已实现或获准
真实 H5 数据接入已实现或获准
S3 自动开工
前端原型可以接入真实业务数据
```

当前已获准的前端可视化原型仍只能是纯展示、无真实数据读写；不得解除禁用控件或通过 API / Repository 触发业务写入。

后续若讨论 S3，必须由产品经理以独立范围发起，并重新冻结 Backup V3、API 错误语义、unknown-outcome、运行时接入、测试与 UAT 门；未经独立授权，持续禁止 S3、Backup V3、API 和真实 H5 数据接入。
