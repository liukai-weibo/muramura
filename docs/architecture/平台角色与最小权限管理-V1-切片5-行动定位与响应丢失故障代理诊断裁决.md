## 二、响应丢失只读诊断事实

### 2.1 现有 harness 行为

`drop-next-completed-write-response` 当前在上游写入响应完整结束并记入 `harness.network` 后，直接执行 `response.destroy()`，此时尚未向 Chromium 发送响应头或响应体。模式在代理收到该请求时即被一次性消费。

### 2.2 隔离 Chromium 诊断

诊断仅使用随机 loopback 端口、纯内存 HTTP 响应和隔离 Chromium；未加载项目服务、未连接 MySQL、未创建文件、数据库或账号。

对“上游 200 完成后、零响应头直接 destroy”的等价实验，实际得到：

- 代理收到两条相同 PUT，而不是一条；
- 每条上游状态均为 200；
- Chromium 对被断开的首次投递记录 `requestfailed: net::ERR_EMPTY_RESPONSE`；
- 浏览器网络栈透明重发 PUT，最终 fetch 才结束；
- socket 在 destroy 前已分配且未结束，destroy 后立即为 destroyed。

因此，现有 harness 第一次请求消费 drop 模式后，Chromium 的透明重发会以 normal 模式进入代理并取得完整 200。API Client 会采用明确成功结果，组件保持成功状态，不会生成 `role-unknown`。这同时解释了页面 8 秒内没有 unknown 提示。该行为是故障代理未稳定制造“单次写入响应体丢失”，不是生产 unknown 分类或渲染缺陷。

### 2.3 单次请求的可复用故障方式

等价隔离实验改为：上游完成后先向浏览器发送既有 200 状态及完整响应体长度，只发送严格少于该长度的响应体前缀，随后断开 socket。实际得到：

- 代理只收到一条 PUT；
- Chromium 先产生 `response: 200`，随后产生 `requestfailed: net::ERR_CONTENT_LENGTH_MISMATCH`；
- fetch 得到 Response，但 `response.json()` 以 `TypeError: Failed to fetch` 拒绝；
- socket 在响应头已发送、响应未结束时被销毁；
- 整个失败在毫秒级完成，不依赖延长 E2E timeout。

现有生产链对此已经具备正确处理：

1. `request()` 的成功响应 JSON 解析错误向上传播；
2. `parseUnknownRoleWrite()` / `parseUnknownSessionsWrite()` 将没有明确 HTTP status 的成功响应解析失败转换为 `ApiClientUnknownOutcomeError`；
3. `isUnknownWriteError()` 将其识别为 unknown；
4. 管理组件把目标锁更新为 `role-unknown` 或 `sessions-unknown`，写入对应 `targetNotices`；
5. 当前目标行渲染冻结的 unknown 文案和显式重读入口，不自动重试。

因此无需修改 API Client、状态模型、组件或生产渲染。
