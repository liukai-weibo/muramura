> 状态：**产品已冻结，授权后端 / Application / Repository 实施；前端等待稳定契约与自动化测试通过后再实施。**  
> 前置条件：P0/P1 数据可信性与备份恢复修复已于 2026-07-21 通过独立 QA 验收。  
> 产品裁决：方法软删除 30 天可恢复；到期删除方法正文与版本正文；保留最小墓碑解释历史关联；备份升级 v2 并兼容 v1。

## 【技术结论：可行】

本任务以最小、可迁移、可恢复的方式实现三段方法生命周期：

```text
正常可用
→ 回收站（30 天内可恢复，不可复用）
→ 已永久清理（方法正文删除，最小墓碑保留历史解释）
```

本任务必须改动 Contracts、Application、Repository、IndexedDB Schema / Dexie Migration 与备份格式；不改事项状态机、不新增方法业务状态、不改方法形成 / 验证 / 修订的产品语义。

## 【一、Contracts 与数据模型】

### 1. Method：增加软删除生命周期

```ts
interface Method {
  // 既有字段不变
  deletedAt?: string
}
```

语义：

- `deletedAt` 不存在：正常可用；
- `deletedAt` 存在且尚未到期：回收站内，正文和版本仍完整存在，但不可复用；
- `Method` 不存在且存在同 ID `MethodTombstone`：已永久清理。

### 2. 新增 MethodTombstone

```ts
interface MethodTombstone {
  methodId: string
  title: string
  permanentlyDeletedAt: string
  versions: MethodTombstoneVersion[]
}

interface MethodTombstoneVersion {
  version: number
}
```

墓碑只允许保存：

```text
原 methodId
最后已知方法名称
永久清理时间
曾存在的版本号集合
```

墓碑明确禁止保存：

```text
Method 正文
步骤
适用情况 / 不适用情况
版本标题与版本正文
sourceReviewId
任何可用于重建方法正文的信息
```

`methodId` 是唯一稳定历史身份：不得新造映射 ID，不得通过名称、时间或文本重新寻找替代方法。

`versions` 用于校验：一个保留的 `MethodApplication.methodVersion` 确实是该方法曾冻结使用的版本。当前模型不存在 `frozenVersionId`，因此本任务继续以结构化复合身份 `(methodId, methodVersion)` 表示实际使用版本，**不新增无必要的版本 ID 关联字段**。

### 3. MethodEvidence：固化关系事实

产品已明确墓碑不保存或依赖可能断裂的 `sourceReviewId`。但现有 `MethodEvidence` 只有 `{ methodId, reviewId }`，在删除全部 `MethodVersion` 后无法可靠区分形成、验证、修订。

因此必须把该关系在写入时固化到证据自身：

```ts
type MethodEvidenceRelation = 'formation' | 'validation' | 'revision' | 'unknown'

interface MethodEvidence {
  // 既有字段不变
  relation?: MethodEvidenceRelation
  methodVersion?: number
}
```

写入规则：

| 动作 | `relation` | `methodVersion` |
|---|---|---|
| 从复盘形成新方法 | `formation` | `1` |
| 仅验证既有方法 | `validation` | 当次验证的当前冻结版本 |
| 验证并主动修订 | `revision` | 新生成的版本 |

约束：

- 新写入证据必须有 `relation` 与 `methodVersion`；
- 历史数据迁移时，能由现有版本与 `sourceReviewId` **唯一可靠还原**的，回填为 `formation` 或 `revision`；
- 存在但不命中版本来源的，回填 `validation` 与当时无法确定时的 `methodVersion` 规则应由实现按已知 Method 当前版本保守处理；若无法可靠确定版本号，则写 `relation: 'unknown'` 且不写 `methodVersion`；
- 一个 review 命中多个版本来源、来源本身异常或其他无法验证的历史记录，必须回填 `unknown`，不得推测；
- 迁移完成后，展示层以 `MethodEvidence.relation` / `methodVersion` 为唯一依据，不再通过 `MethodVersion.sourceReviewId` 反推；
- `MethodVersion.sourceReviewId` 仍保留其现有活跃版本来源用途，并继续按 P0 已验收策略在来源复盘删除时去悬空；它不是墓碑或历史关系读取的依赖。

> 实施前若发现“仅验证”的历史 `methodVersion` 在现有事实中无法可靠回填，应一律降级为 `unknown`，不可按方法当前版本、创建时间或文本猜测。

### 4. BackupData / BackupDocument

```ts
interface BackupData {
  // 既有集合不变
  methodTombstones: MethodTombstone[]
}

type BackupDocument =
  | { format: 'knowledge-base-backup'; version: 1; /* v1 data */ }
  | { format: 'knowledge-base-backup'; version: 2; /* v2 data */ }
```

实现可采用等价的 TypeScript 形状，但必须使版本 1 与版本 2 都可被类型安全地解析，不得继续把版本固定为 `1`。

## 【二、稳定 Application / Repository 契约】

### 1. 方法生命周期命令

在 `MethodRepository` 及其 Application 门面中新增等价能力：

```ts
moveToTrash(methodId: string): Promise<void>
restore(methodId: string): Promise<Method>
listDeleted(): Promise<Method[]>
purgeDeletedBefore(cutoff: string): Promise<void>
```

约束：

- `moveToTrash()` 对不存在、已在回收站或已永久清理的方法必须返回明确错误或幂等结果；选一种风格并全链路一致；
- `restore()` 仅允许 `Method.deletedAt` 存在的对象；墓碑不得恢复；
- `list()` 只返回正常可用方法；
- 回收站读模型须提供方法名称、移入时间、剩余恢复时间所需事实；剩余天数由 Application 或 UI 基于 `deletedAt` 和统一 30 天规则计算，不能成为持久化字段；
- 正常搜索、行动发起和验证 / 修订候选只能使用活跃方法查询。

### 2. 方法应用上下文

冻结为以下等价语义：

```ts
type MethodApplicationContextResult =
  | { status: 'no-association' }
  | { status: 'available'; application: MethodApplication; method: Method; version: MethodVersion }
  | { status: 'method-in-trash'; application: MethodApplication; method: Method; version: MethodVersion }
  | { status: 'method-purged'; application: MethodApplication; tombstone: MethodTombstone }
  | {
      status: 'unavailable'
      application: MethodApplication
      reason: 'method-missing' | 'version-missing' | 'method-and-version-missing'
    }
```

解析优先级：

```text
无 MethodApplication
→ no-association

有活跃 Method 且存在冻结 MethodVersion
→ available

有 Method 且 Method.deletedAt 存在，且冻结 MethodVersion 存在
→ method-in-trash

无 Method 且存在同 methodId MethodTombstone，且应用版本在 tombstone.versions 中
→ method-purged

否则
→ unavailable（保留 application 与准确断裂原因）
```

若存在墓碑但 `application.methodVersion` 不在墓碑版本映射中，属于数据损坏，返回 `unavailable`；不得以“墓碑存在”为由掩盖版本断裂。

### 3. 方法证据历史读模型

`listEvidenceDetails()` 或等价 Application 读模型必须同时支持活跃方法、回收站方法与墓碑方法：

- 通过 `MethodEvidence.relation` 与 `methodVersion` 输出形成 / 验证 / 修订 / 未知；
- 墓碑存在时显示最后名称与“已永久清理”，但不提供方法正文；
- 证据关联的复盘或事项已不存在时，仍按既有降级规则显示关联事实不可读，不伪造内容；
- 不再根据版本 `sourceReviewId`、时间、标题或文案推导 relation。

### 4. 统一回收站读模型

前端不得直接将事项回收站与方法回收站的 Repository 结果自行拼装为业务事实。新增 Application 读模型或由既有数据设置 Application Service 暴露等价查询：

```ts
type TrashEntry =
  | { type: 'item'; id: string; title: string; deletedAt: string }
  | { type: 'method'; id: string; title: string; deletedAt: string }

listTrashEntries(filter: 'all' | 'item' | 'method'): Promise<TrashEntry[]>
```

- 排序统一按 `deletedAt` 倒序；
- 30 天剩余时间从 `deletedAt` 计算；
- 恢复操作根据 `type` 路由到正确 Application 命令；
- 不提前实现分页、复杂搜索或跨对象批处理。

## 【三、Schema 与 Dexie Migration】

新增一个 Dexie 版本（具体版本号基于当前最高版本递增）：

```text
methods：增加 deletedAt 索引
methodTombstones：新增表，主键 methodId，索引 permanentlyDeletedAt
methodEvidence：增加 relation、methodVersion 的持久化字段
```

Migration 必须在单个 upgrade 事务中：

1. 现有 `Method` 默认没有 `deletedAt`，即正常可用；
2. 初始化空 `methodTombstones` 表；
3. 遍历既有 `MethodEvidence` 并按“可可靠证明才回填”的规则写入 `relation` / `methodVersion`；
4. 对无法可靠回填的记录写 `relation: 'unknown'`，不补猜版本；
5. 不删除任何既有方法、版本、证据、应用、事项或复盘；
6. Migration 失败必须让 IndexedDB 升级整体失败，而非半迁移。

实施方必须为 Migration 编写专门测试，覆盖：形成、验证、修订、未知及重复 / 断裂来源等历史数据样本。

## 【四、事务顺序】

### 1. 移入回收站

在方法表写操作中：

```text
读取 Method
→ 校验其存在且未删除
→ 写入 deletedAt / updatedAt
→ 提交
```

不得删除或改写：

```text
MethodVersion
MethodEvidence
MethodApplication
Review
Item
```

### 2. 恢复

```text
读取 Method
→ 校验 deletedAt 存在
→ 移除 deletedAt
→ 更新 updatedAt
→ 提交
```

恢复不创建新版本、不重写证据、不重连关系、不重建正文。

### 3. 到期永久清理

对所有 `Method.deletedAt <= cutoff` 的方法，在同一个多表 `rw` 事务中逐个处理：

```text
读取 Method、其 MethodVersion、MethodEvidence、MethodApplication
→ 构造 MethodTombstone（methodId、title、permanentlyDeletedAt、版本号集合）
→ 校验所有 MethodApplication.methodVersion 均包含于墓碑版本号集合
→ 写入 MethodTombstone
→ 删除该 Method 的全部 MethodVersion
→ 删除该 Method
→ 保留 MethodEvidence 与 MethodApplication
→ 提交
```

事务保护：

- 墓碑写入失败，则方法及版本不得删除；
- 任何应用版本无法被版本映射证明时，整个事务失败并上报；
- 不得为了继续清理而删除应用或证据；
- 不得写入 `sourceReviewId` 到墓碑。

### 4. 事项永久清理与墓碑回收

在现有事项永久清理事务内，保持 P0 已验收逻辑，并增加：

```text
删除即将永久清理事项的 Review、MethodEvidence、MethodApplication、状态事件与 Item
→ 对活跃 MethodVersion 的 sourceReviewId 继续去悬空
→ 统计每个 MethodTombstone 是否仍被任一 MethodEvidence 或 MethodApplication 引用
→ 仅删除无任何有效引用的墓碑
→ 提交
```

重要边界：墓碑不保存 Review ID，因此不需也不得维护墓碑内部的来源复盘引用。

## 【五、备份 v1 / v2 规则】

### v2 导出

- 所有数据导出为 `version: 2`；
- 包含 `methodTombstones`；
- 回收站中的 `Method` 与其完整 `MethodVersion` 正常导出；
- 墓碑只导出冻结的最小字段；
- 导出前 / 导出数据必须满足以下校验不变量。

### v2 严格校验

1. `Method.id` 与 `MethodTombstone.methodId` 不得重复；
2. 每个 `MethodEvidence.methodId` 必须存在于 `Method` 或 `MethodTombstone`；
3. 每个 `MethodEvidence.reviewId` 必须存在；
4. 每个 `MethodApplication.methodId` 必须存在于 `Method` 或 `MethodTombstone`；
5. 每个 `MethodApplication.itemId` 必须存在；
6. 活跃或回收站方法的 `MethodApplication.methodVersion` 必须有对应 `MethodVersion`；
7. 墓碑方法的 `MethodApplication.methodVersion` 必须存在于墓碑 `versions`；
8. 新格式 `MethodEvidence` 的 `relation` / `methodVersion` 必须符合写入不变量；兼容历史 `unknown` 允许不带版本；
9. 墓碑不得携带禁止的正文属性；
10. 所有既有 Item、Review、ItemLink、状态事件与 P0/P1 校验继续严格执行。

### v1 导入

- 接受既有 `version: 1`；
- 归一化为内部 v2 数据形态：`methodTombstones: []`；
- 保留 P0 已验收兼容：仅可选断裂 `MethodVersion.sourceReviewId` 可被清空；
- v1 无 `MethodEvidence.relation` / `methodVersion` 时，使用与 Migration 相同的可靠回填规则；无法可靠还原则 `unknown`；
- 其他必填关系断裂仍严格拒绝；
- 导入成功后的下一次导出必须是 v2；
- 不得从 v1 自动伪造墓碑。

## 【六、自动化测试与验收】

### 数据层自动化

1. 正常、回收站、墓碑、异常断裂四类上下文状态可准确区分；
2. 方法移入回收站后，正常列表、搜索、行动发起和复盘方法候选均排除；
3. 回收站方法的历史关联返回 `method-in-trash` 而非 `unavailable`；
4. 恢复后方法、版本、证据、应用关系原样可用；
5. 方法到期清理创建最小墓碑、删除方法 / 版本正文、保留证据 / 应用；
6. 墓碑方法的历史关联返回 `method-purged`，并能验证应用的版本号映射；
7. `MethodEvidence` 在迁移前后、墓碑清理后仍可输出 formation / validation / revision / unknown，不做时间或文本推断；
8. 来源事项 / 复盘永久清理后，活跃版本 `sourceReviewId` 不悬空，墓碑不含 Review 引用；
9. 墓碑仍有证据或应用引用时不删；最后一条引用删除后才删；
10. v2 导出 → 新库导入 → 再导出结果一致；
11. v1 导入兼容与必填断裂严格拒绝；
12. 迁移样本测试：可靠回填、未知降级、升级原子失败；
13. 人为注入事务错误时，不出现部分墓碑、部分版本删除或孤立引用；
14. 全量 `typecheck`、`test`、`build:h5` 与 `git diff --check` 通过。

### 前端交付前的契约验收

后端完成后须向架构师报告：

```text
最终 Contracts 类型
Application 命令与查询入口
每个状态的返回样例
迁移策略与历史 unknown 数量 / 处理边界
v1 / v2 备份兼容边界
测试命令与实际结果
确认未修改的范围
```

前端只能在此报告审阅通过后开始，且必须：

- 通过 Application 获取 `TrashEntry` 和方法上下文；
- 按 `available / method-in-trash / method-purged / unavailable / no-association` 诚实展示；
- 不直接操作 IndexedDB；
- 不根据 `undefined` 或文本推断关系；
- 不为墓碑提供行动、验证、修订、搜索、编辑或恢复正文入口。

## 【交付给研发的技术约束】

1. 先实现和测试数据层；不得先做 UI 删除入口；
2. 不得因历史数据不完整而猜测关系；使用 `unknown`；
3. 不得把墓碑实现成隐藏完整方法或可恢复副本；
4. 不得删除 Review、MethodEvidence 或 MethodApplication 来规避墓碑校验；
5. 不得放宽备份的必填引用校验；
6. 不得让 `sourceReviewId` 再成为墓碑字段或墓碑读取依赖；
7. 发现既有数据无法满足冻结不变量，立即停止并向架构师报告；
8. 完成后先交 QA 做数据恢复验收，未验收不得交前端实施。
