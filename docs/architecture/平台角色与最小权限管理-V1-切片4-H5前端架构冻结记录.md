## 技术结论

有条件可行。切片 4 可以只复用切片 2 已验收的 `AuthSession.user.roles`、切片 3 已验收的三条管理 HTTP API、现有 Cookie 会话 transport 和单页工作台实现，不需要修改 Contracts、Application、Repository、API、Schema、Migration 或运行配置。

前提是 H5 把服务端会话与管理 API 响应作为唯一可信事实：前端 roles 只用于入口预门控，最终管理权限始终由服务端决定；任何管理 401/403 都必须销毁管理页面内存状态，任何写入结果未知都不得按请求体乐观更新或自动重试。

当前 `knowledge_base` 与 `knowledge_base_uat` 均为 15 表、`schemaVersion=5`、平台表 0，真实 006 未执行。当前 API 不得以切片 1–3 新源码重启或替换。本记录仅冻结前端实现边界，不授权编码、真实联调或任何运行操作。

## H5 API Client 冻结

`apps/client/src/pages/index/api-client.ts` 只允许补充：

```ts
listPlatformUsers(
  input: { page: number; query?: string },
  signal?: AbortSignal
): Promise<PlatformUserPage>

setPlatformUserRoles(
  targetUserId: string,
  input: AdminSetUserRolesRequest
): Promise<PlatformUserSummary>

revokePlatformUserSessions(
  targetUserId: string,
  input: AdminRevokeUserSessionsRequest
): Promise<AdminRevokeUserSessionsResponse>

setApiClientAdminForbiddenHandler(
  handler: ((error: ApiClientError) => void) | undefined
): () => void
```

调用边界固定如下：

- 列表只请求 `GET /admin/users?page={positiveInteger}`；trim 后非空 query 才追加经 `encodeURIComponent` 或 `URLSearchParams` 编码的 `query`。不得发送 pageSize、userId、roles 或其他参数。
- 角色只请求 `PUT /admin/users/{encodeURIComponent(id)}/roles`，body 精确为 `{ roles, operationId }`。
- 会话只请求 `POST /admin/users/{encodeURIComponent(id)}/revoke-sessions`，body 精确为 `{ operationId }`。
- operationId 不在 API Client 内生成；API Client 只传输最终确认产生的值。
- 不读取或保存 Cookie，不设置 Authorization/JWT，不接受 actorUserId，不把目标 id 写入 query 或 body。
- 三个方法均不自动重试；写方法不因组件卸载主动 Abort。浏览器断线、Abort、超时或响应丢失继续转为既有 `ApiClientUnknownOutcomeError`。
- 写请求收到 HTTP 503 时，由管理状态层按 unknown-outcome 处理；401/403、404、409 等已收到的标准错误仍保留 `status/code/message/requestId`。
- 仅当路径以 `/admin/` 开头且响应为 403、并且请求仍属于当前认证上下文时，才以已解析的 `ApiClientError` 触发 admin forbidden handler；由父级安全页面读取其中的 message/requestId。不得把其他业务 403 当作管理权限撤销。
- 401 继续使用既有 unauthorized handler，不新增第二套登录状态。

API Client/Adapter 必须做最小运行时校验：

- `PlatformUserPage` 必须含非负安全整数 total、正整数 page、精确 `pageSize=20` 与 items 数组；返回 page 必须等于请求 page。
- 每个 `PlatformUserSummary` 的 id、username 必须为非空字符串，createdAt 必须是可解析的 ISO 时间字符串；同页 id 不得重复；roles 只接受精确 `['member']` 或 `['member','platform_admin']`。
- 列表响应任一项缺 member、角色顺序异常、字段不可读或结构异常时，整次读取失败，不得降级为成员或部分列表。
- 角色 200 响应必须为合法 `PlatformUserSummary` 且 id 与请求 targetUserId 相同。200 响应无法解析、结构非法或 id 不匹配时，因写入可能已提交，必须转为角色 unknown-outcome。
- 会话 200 响应的 revokedSessionCount 必须是非负安全整数。无法解析或结构非法时必须转为会话 unknown-outcome。

前端只显示 username、角色文案与 createdAt；id 只作 React key、响应匹配和管理 API 路径，不得渲染、复制或进入搜索条件。

## 认证角色门与 401/403 卸载

入口和页面装载规则固定为：

- “用户管理”仅在当前 `AuthSession.user.roles` 精确包含 `platform_admin` 且当前认证上下文未记录管理 403 时显示。
- `member` 不装载管理组件，不发管理请求，也不渲染列表、骨架、空态或操作入口。
- 入口只是前端预门控，不是权限判定。管理员首次进入后必须以真实管理列表 GET 成功建立可展示事实。
- 当前登录用户以 `session.user.id` 与条目 id 精确比较；该行只显示“当前账号”，不渲染任何角色或会话写入口。
- 不按 username、历史入口、旧列表、角色标签文案或本地缓存推断当前管理员。

401 边界：

- 任一管理请求返回 401 时继续触发既有 `enterUnauthenticatedGate`。
- 必须同步使管理组件失效并卸载，清除列表、query draft/applied query、页码、确认层、请求控制器、目标锁、unknown-outcome 与提示。
- 旧管理 GET/写响应即使随后到达也不得重新挂载页面或写回状态。

403 边界：

- 任一 `/admin/**` 请求返回 403 时，admin forbidden handler 立即在当前认证工作区设置 `managementAccessDenied=true`，切回安全默认模块“行动”，隐藏入口并销毁管理组件实例。
- 销毁必须清除列表、搜索、分页、确认层、读请求、目标写锁和两类 unknown-outcome；不得在其他模块保留可恢复的管理快照。
- 页面只在安全默认模块显示一次冻结提示“你的管理员权限已变化，无法继续访问用户管理。”及服务端 requestId；不得自动重试或把 403 转为登录失败。
- `managementAccessDenied` 在当前认证上下文内保持失败关闭；只有新的真实认证上下文（重新登录或页面重新启动后成功读取 session）才能重新根据最新 roles 决定入口，不能由前端按钮自行清除。
- 403 写响应是服务端明确拒绝，不归类 unknown-outcome；页面仍必须卸载。

普通模块内导航可以隐藏已访问的管理组件但应在同一认证上下文内保留其内存状态，以免丢失正在提交或结果未知事实；隐藏状态不得自动读取或写入。401、403、明确退出、认证上下文替换与浏览器卸载必须真正销毁。浏览器卸载不触发保存、补偿或重试。

## 用户列表、搜索和分页状态

前端状态最小分离为：

```text
access: eligible | denied
list: absent | initial-loading | ready | refreshing | initial-error | refresh-error
snapshot: PlatformUserPage | undefined
queryDraft: string
appliedQuery: string
page: positive integer
readGeneration: monotonic integer
readAbortController: current GET only
confirmation: none | grant-role | revoke-role | revoke-sessions
targetLocks: Map<userId, TargetWriteState>
```

搜索与分页规则：

- queryDraft 只反映输入，不触发请求；最多 80 个 JavaScript 字符单元，超限输入保持原合法值。
- Enter 或“搜索”把 trim 后值写入 appliedQuery、将 page 置 1，再发一次 GET。空值等同未筛选。
- “清除搜索”同时清空 draft/applied query、回到第 1 页并发一次明确 GET。
- 翻页只改变 page，保留 appliedQuery；固定每页 20，不产生 pageSize、跳页或无限滚动。
- 工具栏“刷新”只重读当前 appliedQuery/page，不提交尚未搜索的 queryDraft。
- total 页数按 `ceil(total/20)` 展示；total 为 0 时显示第 1/1 页。服务端返回超过末页的空 items 时保留当前 page 与真实 total，允许上一页，不伪造 404 或自动改页。
- 初次读取无 snapshot 时显示骨架；已有 snapshot 的搜索、翻页或刷新保留旧内容并标明正在读取。读取失败保留 draft、applied query、page 和旧 snapshot。
- 未搜索 total=0 与搜索无结果必须依据 appliedQuery 分开呈现。

每次 GET 必须：

1. Abort 上一个列表 GET。
2. 递增 readGeneration，并捕获当前认证上下文、page、appliedQuery 与事实代次。
3. 仅当未 Abort、组件仍属于同一认证上下文、generation 最新且请求上下文仍匹配时应用响应。
4. Abort 只作为旧读取取消，不显示读取失败；其他读取错误按初次或保留旧列表错误态显示。

不得由返回时间先后、用户名、数组位置或页码猜测新旧关系。

## operationId、确认层与目标级写锁

确认层必须冻结打开时的 `targetId`、`targetUsername`、action 与 expectedRoles；最终确认前再次从当前 snapshot 按 id 校验目标仍存在、仍非当前用户且角色仍与 action 相容。校验失败时关闭确认层并要求显式刷新，不发送写请求。

operationId 规则：

- 打开、取消、遮罩点击和查看确认层均不生成 operationId。
- 最终确认函数先以同步 ref 原子占用 targetId，再生成一次规范 UUID，随后才构造 body。优先使用 `globalThis.crypto.randomUUID()`；其不可用时只允许以 `crypto.getRandomValues()` 的 CSPRNG 字节生成符合 RFC 4122 version/variant 位的 UUID v4。
- `randomUUID` 与 `getRandomValues` 均不可用时明确阻止写入并提示；不允许使用时间戳、Math.random、requestId、userId 或其他弱随机替代。
- 每次重新确认生成新 UUID；任何错误或 unknown-outcome 后都不得复用旧 operationId。
- operationId 只保留在本次尝试的内存 token 中，不渲染、不持久化、不进入日志。

目标写状态固定为：

```text
idle
submitting-role
submitting-sessions
role-unknown
sessions-unknown
```

- 同一 userId 任一非 idle 状态都禁用该目标全部角色与会话入口。
- 同步 ref 是防双击的最终门，不能只依赖异步 React state；按钮、Enter、遮罩和重复事件必须共享同一提交函数。
- submitting 时确认层不可取消、关闭或切换目标；普通页面导航只隐藏而不销毁状态，不得 Abort 写请求。
- 不同目标使用不同锁；不得用一个目标的结果、错误或 requestId 解锁另一个目标。
- 每次写尝试另有不可复用的本地 attempt token。只有 targetId、action 和 token 全部匹配的当前响应才能改变目标状态。
- 写开始时递增事实代次；此前启动的列表 GET 即使后到也不得覆盖写入后的目标事实。

明确角色成功：先运行时校验响应，再只用服务端 `PlatformUserSummary` 按 id 替换当前 snapshot 中目标行，清除该目标锁和确认层；不得按请求 body 修改 roles，也不得自动重读整页。

明确会话成功：只用 `revokedSessionCount` 显示冻结成功文案，列表结构和角色不变，清除该目标锁和确认层；不得创建会话数量常驻状态。

明确 400/404/409 或其他非 401/403/503 标准错误：保留写前 snapshot，清除 submitting 锁，显示服务端 message/requestId；404/409 提供显式刷新，不自动移除、修复或重试目标。

## 两类 unknown-outcome 边界

共同进入条件仅限写请求的 transport 失败、Abort、超时、响应丢失、HTTP 503，或 HTTP 2xx 后响应无法可信校验。共同规则：保留写前列表，不显示成功/失败、不自动重试、不按 body 改写、不复用 operationId，并保留服务端已提供的 requestId。

### 角色 unknown-outcome

- target 状态转为 `role-unknown`，角色标签继续显示写前事实，全部目标写入口保持锁定。
- 只能由用户显式触发既有用户列表 GET 确认。只有一次新的成功 GET 返回同一 targetId 的合法 `PlatformUserSummary`，才能以其 roles 更新目标并解除锁。
- GET 成功但未包含 targetId，不能证明角色事实，保持旧列表、警示和锁；GET 失败、Abort、401/403 同样不得解锁，其中 401/403执行前述卸载。
- 普通刷新、搜索或翻页响应若是在该 unknown 状态形成之前启动，不得作为确认事实。确认读取必须捕获形成 unknown 后的新事实代次。
- 不提供“再次提交角色变更”；用户必须先通过显式 GET 解锁，再重新打开确认层产生全新操作。

### 会话 unknown-outcome

- target 状态转为 `sessions-unknown`，提示“无法确认会话撤销是否完成”，全部目标写入口保持锁定。
- 用户列表不包含会话事实；任何列表 GET、角色变化或页面刷新都不得把它解释为会话撤销成功，也不得自动解锁。
- 只允许用户点击明确的“再次撤销会话”动作，重新打开完整会话确认层。该动作表示用户知悉前次仍未知，并把目标从 unknown 转入新的待确认上下文；此时仍不生成 operationId。
- 只有用户再次点击最终确认时才生成新的 UUID 并发出一条新请求。取消新确认后恢复 `sessions-unknown`，不能静默变为 idle。
- 不新增会话查询、审计查询、设备列表、补偿写入或成功推断。

最低测试范围：

1. API Client 精确请求三条既有路由，Cookie 同源，ID/query 编码正确，不发送 pageSize、actorUserId、Cookie、审计值或额外字段；每次只发一条请求且无自动重试。

3. 角色/会话 2xx malformed、id 不匹配、transport/Abort/503 分别进入对应 unknown；404/409 保持明确失败且保留 message/requestId。
4. member 无入口、无管理组件、无管理 GET；admin 有入口。当前账号按服务端 id 隐藏所有操作，不按 username 判断。
5. 管理 GET 的 401 清空整个认证工作区并进入登录门；管理 GET/写的 403 隐藏入口、卸载列表/搜索/确认/锁、返回行动模块，旧响应不能复活页面。

7. query draft 与 applied query 分离；Enter/按钮单次读取、新搜索 page=1、清除搜索单次读取、翻页保留 query、刷新不提交未搜索 draft。
8. 快速搜索→翻页→刷新以及响应乱序时，Abort 与 generation 保证只有最新上下文可见；认证上下文变化后所有旧响应失效。
9. 最终确认前不生成 UUID；双击/重复 Enter/遮罩只产生一个 UUID、一条 POST/PUT；覆盖 randomUUID 与 CSPRNG UUID v4 路径，二者均不可用时零请求。
10. 当前快照目标变化、目标成为自己、角色与确认动作不相容时零请求并要求刷新；响应 targetId 不匹配按角色 unknown 处理。
11. target A 提交/unknown 不锁 target B；A 的旧响应不解锁 B，也不能覆盖较新的 A attempt。
12. 角色明确成功只采用响应摘要；会话明确成功只采用响应计数；两者均不自动 GET。
13. 角色 unknown 保留旧角色和目标锁，无自动重试；仅 unknown 形成后的显式 GET 且包含同一 id 才解锁，缺目标或读取失败继续锁定。
14. 会话 unknown 不被任意列表 GET 解锁；再次操作必须重新展示完整确认层，取消后仍 unknown，最终再次确认生成新 UUID。
