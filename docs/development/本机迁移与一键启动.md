# 本机迁移与一键启动

日常运行仅使用 `.env` 中的 `knowledge_base`。`.env.uat` 和 `knowledge_base_uat` 仅供隔离 UAT；若 32146 已被 UAT 或未知 API 占用，日常启动会拒绝，绝不会停止或接管该进程。

首次在干净目录准备：

1. 克隆代码并安装 Node 22、Corepack、Docker Desktop；执行一次 `corepack enable`，再执行 `pnpm install`。
2. 执行 `pnpm setup`。它只会在 `.env` 缺失时复制 `.env.example`，随后退出。
3. 仅在本机编辑新生成的 `.env`，填写自己的本地密码；不要提交、复制或分享该文件。
4. 数据库创建与 Migration 继续使用既有受控流程。已有环境必须先确认实际 MySQL、数据库和 Schema，不允许由启动器自动迁移或根据 Compose 名称猜测数据源。
5. 再次执行 `pnpm setup`，确认日常配置有效且 MySQL 可达。

WSL/Linux 日常使用：保持日常 MySQL 运行，执行 `pnpm dev`。Node 启动器在同一终端前台启动 API 和 H5，先确认 `/health` 为 `ready`、`knowledge_base` 且 `schemaVersion` 为正整数，再启动 H5；按 `Ctrl+C` 只停止本次创建的 API/H5。MySQL 的启动、停止和 Migration 继续按当前运行事实单独管理，不由开发启动器猜测或切换。原生 Windows 前台编排当前失败关闭，应在 WSL/Linux 中运行。

旧 `kb-init.ps1`、`kb-start.ps1`、`kb-stop.ps1` 已归档至 `archive/scripts/windows-local-launcher/`，仅保留历史实现，不再作为活动启动或恢复入口。

2026-08-04 本机实测当前服务为 `ready / knowledge_base / schemaVersion=9`，API 与 H5 的进程树由 `pnpm dev → scripts/local-dev.mjs` 启动。该事实只说明当前本机运行条件已满足，不授权其他机器跳过 `.env`、数据库身份和 Schema 检查。注册账户、授予平台管理员、Backup restore 和 owner claim 都不属于日常启动步骤；`knowledge_base_uat` 使用独立 `.env.uat`，不得由本启动器切换或接管。

API 直接启动失败时，本机终端会输出脱敏的结构化诊断，区分 Migration 记录表缺失、Schema 版本落后、必需表缺失、MySQL 配置缺失/无效、MySQL 不可用、API 端口冲突、监听地址不合规与未分类错误。诊断不输出密码、账号、host、原始 SQL、MySQL 原始 message、stack 或完整 environment，也不会自动运行 Migration 或重试。

需要在 WSL/Linux Shell 中单独启动 API 时，先加载配置：`set -a && source .env && set +a`（UAT 用 `.env.uat`），再执行 `pnpm api`。标准入口会自动使用上述诊断格式。若开发调试必须通过 `tsx -e` 导入 `startApiMain()`，自定义 catch 应同时导入并调用 `formatApiStartupFailure(error)`；直接 `console.error(error)` 会绕过入口格式化并由 Node 打印原始错误对象与堆栈。

`pnpm setup` 和 `pnpm dev` 都不会自动查找、读取或恢复 Backup。需要恢复时必须通过现有产品入口显式选择并确认合法 Backup，不能把恢复混入启动流程。

新启动器不写 PID 状态或持久日志，API/H5 日志只输出到当前终端且必须保持脱敏。不要复制、提交或同步 `mysql-data`、实际 `.env`、密码、日志、临时状态或个人 Backup；不要执行 `docker compose down -v`。
