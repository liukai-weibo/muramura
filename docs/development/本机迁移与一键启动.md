# 本机迁移与一键启动

日常运行仅使用 `.env` 中的 `knowledge_base`。`.env.uat` 和 `knowledge_base_uat` 仅供隔离 UAT；若 32146 已被 UAT 或未知 API 占用，日常启动会拒绝，绝不会停止或接管该进程。

首次在干净目录演练：

1. 克隆代码并安装 Node、Corepack、Docker Desktop；执行 `corepack pnpm install`。
2. 执行 `powershell.exe -NoProfile -File scripts/kb-init.ps1`。它只会在 `.env` 缺失时复制 `.env.example`，随后退出。
3. 仅在本机编辑新生成的 `.env`，填写自己的本地密码；不要提交、复制或分享该文件。
4. 再次执行 `powershell.exe -NoProfile -File scripts/kb-init.ps1`。该动作只通过既有 `docker compose up -d mysql` 启动 MySQL；仅在没有 Schema 的空日常库执行既有 migration。
5. 日常服务启动后检查 `Invoke-RestMethod http://127.0.0.1:32146/health`，必须为 `ready`、`knowledge_base` 且 `schemaVersion` 为正整数；当前源码的唯一最低版本门为 Schema 7，API 未通过该门时不会监听。启动器不复制具体版本常量，只输出已验证 health 的实际 `schemaVersion`。H5 静态入口是 `http://127.0.0.1:10086/index.html`。

日常使用：执行 `powershell.exe -NoProfile -File scripts/kb-start.ps1` 启动 MySQL、API、H5。执行 `powershell.exe -NoProfile -File scripts/kb-stop.ps1` 只停止该启动器记录并验证过的 API/H5 子进程；如明确需要停 MySQL，使用 `-StopMySql`，它仅运行 `docker compose stop mysql`。

当前开发库为空业务、空账户的 Schema 6，运行中的旧 API 仍以该版本提供服务；当前源码已要求 Schema 7，在 Migration 007 获得独立运行库执行授权并完成前不得用当前源码重启 API。注册账户与授予平台管理员不属于日常启动步骤。业务集合全空时无需 initial owner claim，启动器不得自动执行 claim。`knowledge_base_uat` 使用独立 `.env.uat`，不得由本启动器切换或接管。

API 直接启动失败时，本机终端会输出脱敏的结构化诊断，区分 Migration 记录表缺失、Schema 版本落后、必需表缺失、MySQL 不可用、API 端口冲突与未分类错误。诊断不输出密码、账号、host、原始 SQL、MySQL 原始 message、stack 或完整 environment，也不会自动运行 Migration 或重试。

需要单独启动 API 时优先执行 `corepack pnpm api`，该标准入口会自动使用上述诊断格式。若开发调试必须通过 `tsx -e` 导入 `startApiMain()`，自定义 catch 应同时导入并调用 `formatApiStartupFailure(error)`；直接 `console.error(error)` 会绕过入口格式化并由 Node 打印原始错误对象与堆栈。

恢复个人 Backup 必须明确提供文件：`powershell.exe -NoProfile -File scripts/kb-init.ps1 -BackupPath C:\path\backup-v3.json`。脚本先拒绝非 V3，再确认日常十个业务集合为空后才调用既有恢复接口。不会自动查找、读取或恢复任何备份。

状态和日志位于系统临时目录 `knowledge-base-local-start`，不记录密码、Backup 内容或业务数据。不要复制、提交或同步 `mysql-data`、实际 `.env`、密码、日志、临时状态或个人 Backup；不要执行 `docker compose down -v`。
