# 个人系统 Web 项目开发流程 v1

## 总原则

> 先证明最小闭环，再增加范围；先写清规则和验收标准，再写页面；每个阶段都必须形成可运行、可测试、可回退的结果。

不要按“把所有功能都写完，最后一起测试”的方式开发。

## 阶段 0：确认边界

### 目标

把模糊愿望变成可以判断完成与否的产品范围。

### 要做的事

1. 审核 `功能清单-v1.md`
2. 确认第一版只做：想法、执行、复盘、方法、导出恢复
3. 回答架构设计末尾的产品问题
4. 选定项目名称和本地运行方式
5. 明确哪些内容第一版不做

### 产出

- 已确认的功能清单
- 第一版不做清单
- 5—10 条核心用户故事
- MVP 完成标准

### 通过标准

任何新需求都能判断：属于 MVP、第二阶段，还是以后再做。

## 阶段 1：画清业务流程

### 目标

在写代码前确认系统规则没有自相矛盾。

### 要做的事

1. 确定事项的全部状态
2. 确定允许和禁止的状态跳转
3. 确定复盘如何产生方法和新想法
4. 确定归档、放弃、暂停和恢复的规则
5. 用“学习瘦金体”完整走一遍纸面流程

### 产出

- 状态图
- 状态转换表
- 核心名词表
- 异常场景清单

### 通过标准

不打开代码，也能清楚回答任意事项下一步可以去哪、为什么。

## 阶段 2：低保真页面设计

### 目标

先确认信息和操作的位置，不先做视觉包装。

### 要做的页面

1. 总览页
2. 想法列表
3. 正在做列表
4. 待复盘与已复盘列表
5. 事项详情与时间线
6. 复盘表单
7. 方法列表与详情
8. 导出和恢复页

### 设计要求

- 使用灰度线框图即可
- 每页明确主要任务
- 每页只有一个最重要操作
- 先设计桌面端
- 不提前做动画、主题和复杂图表

### 通过标准

使用静态线框图可以完整演示 MVP 十步流程。

## 阶段 3：数据模型和技术验证

### 目标

在搭完整项目之前，验证最危险的技术假设。

### 优先验证

1. IndexedDB 的 Schema 升级与 Dexie 版本迁移
2. 状态变化写入事件历史
3. 复盘与方法的多对多关联
4. Markdown 导出目录结构
5. JSON 备份后完整恢复
6. Taro H5 构建并通过 Docker 镜像运行

### 产出

- IndexedDB Schema v1
- 第一份 Dexie 版本迁移
- 种子数据
- 导出恢复原型
- H5 Docker 构建原型
- 架构决策记录

### 通过标准

在测试环境中创建一条想法、完成完整流转、导出、清空 IndexedDB 并恢复，恢复后关联不丢失；同一 H5 构建产物能够通过本地预览和 Docker 访问。

## 阶段 4：搭建项目骨架

### 目标

建立统一的代码规范和验证通道。

### 要做的事

1. 创建 Taro + React + TypeScript Monorepo
2. 配置格式化、Lint 和类型检查
3. 配置 Dexie、IndexedDB Schema 和数据版本迁移
4. 配置 Vitest 与适合 Taro H5 的端到端测试
5. 建立核心规则、数据接口和平台适配层
6. 配置 `.env.example`、`.gitignore` 和 `.dockerignore`
7. 建立 Markdown + JSON 导出恢复
8. 建立 H5 的 Docker 多阶段构建

### 基础命令应包含

```text
H5 开发
H5 构建与预览
微信小程序开发与构建（后续启用）
类型检查
Lint
单元测试
端到端测试
数据 Schema 迁移测试
数据导出与恢复测试
Docker 镜像构建
```

### 通过标准

新电脑按照 README 可以启动 H5、初始化 IndexedDB、运行全部测试并构建 Docker 镜像。

## 阶段 5：按纵向闭环开发

不要先写完全部存储层，再写全部业务逻辑，最后写全部页面。应该每次完成一条从界面到存储适配器的完整小闭环。

### 第一个闭环：想法

- 创建想法
- 查看列表和详情
- 在两种想法状态间切换
- 写入事件历史
- 单元测试和端到端测试

### 第二个闭环：开始执行

- 从想法转为进行中
- 填写阶段目标、下一步和停止条件
- 暂停、恢复和放弃
- 状态规则测试

### 第三个闭环：结束执行

- 选择需要复盘或无需复盘
- 进入待复盘或归档
- 时间线正确显示

### 第四个闭环：复盘

- 填写并完成复盘
- 事项变为已复盘
- 从复盘生成新想法

### 第五个闭环：方法

- 从复盘生成或关联方法
- 查看方法及其证据
- 方法产生新想法

### 第六个闭环：导出恢复

- 完整导出 Markdown + JSON
- 生成清单和校验报告
- 恢复前自动备份
- 清空测试库后恢复并核对数量和关联

每个闭环都必须：

1. 有明确验收条件
2. 有规则测试
3. 有至少一条端到端测试
4. 可以独立演示
5. 代码通过类型检查和构建

## 阶段 6：总览、搜索和基础可视化

### 目标

闭环稳定以后，再提高使用效率和可见性。

### 要做的事

- 总览卡片和数量
- 最近更新
- 搜索和筛选
- 状态看板
- 单事项流转时间线
- 空状态、错误提示和确认操作

### 通过标准

不依赖数据库工具，用户能从网页理解当前系统状态并完成所有日常操作。

## 阶段 7：真实使用验证

### 目标

验证系统是否适合 KKK，而不是只验证代码能运行。

### 建议周期

连续真实使用 2—4 周。

### 观察问题

- 是否真的愿意记录想法？
- 从想法转执行是否顺手？
- 待复盘是否越积越多？
- 哪些字段从来不填？
- 哪些字段总想补充？
- 方法是否真的会被回看？
- 导出内容是否适合 AI 阅读？
- 系统是否减少了认知负担？

### 规则

- 先记录摩擦，不立即新增功能
- 同一问题重复出现三次，再考虑改产品
- 优先删除无用字段，而不是不断增加字段

### 通过标准

核心闭环经过真实数据验证，确认不是只在设计层面成立。

## 阶段 8：决定第二阶段

真实验证后，再决定优先加入哪一个模块：

- 关于我和长期方向
- 我想学的人和东西
- 年、月、周计划
- 附件
- AI
- 云同步

一次只选一条主线，不并行扩张全部模块。

## 每个功能的标准开发步骤

以后任何功能都按下面顺序：

1. 写清用户为什么需要
2. 写出一到三个用户故事
3. 定义完成标准和不做范围
4. 检查是否影响现有数据模型
5. 画低保真交互
6. 先写核心规则测试
7. 实现最小纵向闭环
8. 运行类型检查、测试和构建
9. 使用真实数据验证
10. 更新文档和架构决策记录

## 分支与提交建议

即使只有一个人，也保持小批次改动：

- 一个功能或修复一个分支
- 一次提交只表达一个清晰变化
- 数据 Schema 迁移和对应代码一起提交
- Dockerfile、构建脚本和应用构建变化保持同步
- 不把重构、新功能和格式化混在一次提交
- 合并前必须通过类型检查、测试和构建

## 第一轮开发任务顺序

```text
P0-01 确认功能范围与名词
P0-02 确认状态机
P0-03 画 MVP 页面线框
P0-04 设计并验证 IndexedDB Schema
P0-05 验证导出、恢复和 Docker 构建
P0-06 搭建项目骨架
P0-07 实现想法闭环
P0-08 实现执行闭环
P0-09 实现复盘闭环
P0-10 实现方法与证据关联
P0-11 实现完整导出恢复
P0-12 完成总览、搜索和时间线
P0-13 用真实数据运行 2—4 周
```

## 防止项目失控的边界

出现以下情况时停止写新功能，回到产品和架构层：

- 同一概念出现三个不同名字
- 同一份数据需要在多个模块复制
- 新功能无法说明服务哪个核心问题
- 页面越来越多，但核心流程仍不能完整运行
- 为了一个未来可能需要的场景引入复杂架构
- 测试无法稳定复现状态流转
- 导出后无法理解或恢复数据
- 开发系统本身开始挤占使用系统的时间

## 当前下一步

不是马上创建全部页面，而是依次完成：

1. KKK 审核 `功能清单-v1.md`
2. 确认整体架构中的待确认问题
3. 把状态转换整理成正式状态表
4. 画八个核心页面的低保真图
5. 验证 IndexedDB、导出恢复和 Docker 镜像原型
6. 通过后再创建正式 Taro Web 项目
